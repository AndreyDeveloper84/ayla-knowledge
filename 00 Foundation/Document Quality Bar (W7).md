# Document Quality Bar — обязательная самопроверка перед сдачей документа

Дистилляция вердиктов владельца (ADR-0012 v0.1→v0.2, AMD-020 v0.1 reject).
Документ НЕ сдаётся оркестратору, пока автор не прошёл каждый пункт и не
приложил ответы в отчёт. Назначение: устранить классы переделок, а не
добавить бюрократии — каждый пункт происходит из реального возврата.

## A. Честность scope

- A1. Заголовок и заявления ≤ фактический scope. Перечислены покрытые
  классы/системы И отдельно — заведомо НЕ покрытые (с причиной/статусом).
- A2. Слова «полный / complete / исчерпывающий / полный контракт» —
  только при реестре, доказывающем полноту. Иначе — узкое название +
  дисклеймер, чем документ НЕ является.
- A3. Запрещено утверждение «конфликтов не обнаружено» при наличии ЛЮБОГО
  открытого решения/блокера. Форма: «конфликтов, препятствующих review,
  нет; канонизация заблокирована пунктами X, Y».
- A4. Норма = факт (код/источник) или явно помеченный design candidate.
  Канонизация несуществующего поведения — с секцией implementation
  prerequisites (что должно смержиться до вступления в силу).

## B. Юридическая полнота (семья 152-ФЗ и смежное)

- B1. Каждая затронутая статья закона замаплена на раздел (ст. 14 доступ,
  ст. 21 удаление, ст. 9 согласие, ст. 20 уведомление и т.д.).
- B2. Различать: data-portability выгрузку ≠ формальный ответ на запрос
  субъекта. Если документ заявляет реализацию прав — схема ответа включает
  цели, основания, способы, сроки, получателей, трансграничность,
  автоматические решения.
- B3. Зафиксировано: кто оператор, кто обработчик по поручению, кто
  получает формальный запрос, кто отвечает за сроки, кто уведомляет
  третьих лиц.
- B4. Каждый retained-класс данных: основание + срок + ограничения
  использования. «Retention TBD» — только с владельцем решения и
  дедлайном, не как пустое место.

## C. Глубина безопасности

- C1. Для деструктивных/чувствительных операций: срок действия токена,
  replay-защита, step-up/подтверждение, nonce операции, rate limit,
  поведение при relink/смене устройства.
- C2. Error taxonomy: auth-инциденты и contract violations НЕ маскируются
  под «временную недоступность». Каждый класс ошибок — свой код/исход.
- C3. Персональных значений нет в URL, логах, метриках, трейсах — норма
  + acceptance-проверка.
- C4. 4xx-статусы не приравниваются к смысловым исходам без машинно
  различимого кода (404 ≠ «успешно удалено» без `subject_gone`).

## D. Конкурентность и жизненный цикл

- D1. Для многошаговых операций — анализ гонок и barrier/блокировка/
  state machine (или доказательство атомарной безопасности порядка).
- D2. Идемпотентность — механика, не концепт: ключ, одновременные вызовы,
  потерянный ответ, корреляция retry (operation_id), срок хранения
  idempotency record.
- D3. Полный жизненный цикл удаления: soft-delete → hard-delete SLA →
  purge-job → кэши/индексы/embeddings/derived/backup. Состояния
  deletion_state перечислены.
- D4. Retention manifest: что остаётся, почему, до когда, с какими
  ограничениями. Пользователь/читатель не получает ложное «всё удалено».

## E. Контракты ответов

- E1. Закрытая схема success И закрытая схема partial/failure (не только
  happy path). Per-step результаты для каскадов.
- E2. operation_id/correlation для распределённых операций.

## F. Acceptance-батарея

- F1. Сверх happy path: конкурентный запуск, потеря ответа + retry,
  отказ каждого шага по очереди, replay устаревших креденшелсов,
  cross-tenant completeness, поведение после завершения (re-auth,
  re-export, re-write), PII-в-логах.

## G. Процесс

- G1. Ноль открытых owner decisions на момент сдачи — иначе документ
  маркируется blocked, а не «готов к решению».
- G2. Validation репозитория: 0 errors, warnings не выше baseline.
- G3. Отчёт по форме: что реализовано, что design candidate, что
  отклонено из брифа и почему, подтверждение запретов.

## Применение

- Каждый промпт W7 ссылается на этот документ как нормативный вход.
- Оркестратор ревьюит по нему же — вердикт по пунктам A–G.
- Изменения — версионно (v1.0 → v1.1), только оркестратором с GO владельца.
