# 2. Purpose, Scope and Audience

## 2.1. Purpose

Цель настоящего документа — определить единую каноническую доменную модель
экосистемы Ayla, используемую всеми продуктами, сервисами, репозиториями и
командами разработки.

Документ устанавливает:

- единый Ubiquitous Language;
- канонические определения доменных понятий;
- границы Core Domain, Supporting Domains и Generic Domains;
- правила моделирования Entities, Value Objects, Aggregates и Domain Events;
- доменные инварианты;
- жизненные циклы (Lifecycle) доменных сущностей;
- принципы владения (Ownership) и ответственности (System of Record);
- правила сопоставления доменной модели с техническими представлениями.

Основная цель документа — обеспечить единое понимание предметной области и
исключить расхождения в трактовке доменных понятий между продуктовой,
архитектурной и инженерной документацией.

...

## 2.2. Primary Objective

После ознакомления с данным документом любой участник проекта должен
однозначно понимать:

- что представляет собой каждое доменное понятие;
- где проходят границы ответственности между доменными контекстами;
- какие объекты являются Entities, Value Objects, Aggregates и Domain Events;
- какой жизненный цикл имеет каждая значимая сущность;
- какие бизнес-инварианты обязательны для соблюдения;
- какой компонент является System of Record для каждого доменного объекта;
- каким образом доменная модель отображается на API, базы данных, UI и AI Runtime.

...

## 2.3. Scope

Настоящий документ распространяется на все существующие и будущие компоненты
экосистемы Ayla, использующие каноническую доменную модель, включая:

- клиентские приложения;
- AI Concierge;
- Recommendation Engine;
- Service Catalog;
- Specialist & Provider Management;
- Appointment Management;
- Personal Context и Memory;
- Consent Management;
- Conversation Runtime;
- Feedback и Outcome Processing;
- Governance, Privacy и Safety.

Документ является обязательным для всех репозиториев и сервисов,
использующих каноническую доменную модель Ayla.

...

## 2.4. Out of Scope

Настоящий документ не определяет:

- структуру баз данных;
- модели ORM;
- REST, GraphQL и иные API-контракты;
- DTO и транспортные модели;
- пользовательские интерфейсы;
- Prompt Engineering;
- Tool Schemas;
- внутреннюю реализацию сервисов;
- детали алгоритмов ранжирования, AI-моделей и инфраструктуры.

Указанные аспекты должны опираться на настоящую спецификацию, но не
являются частью её нормативной области.

...

## 2.5. Audience

Документ предназначен для:

- Product Owner;
- Product Manager;
- Business Analyst;
- Domain Architect;
- Backend Engineer;
- Frontend и Mobile Engineer;
- AI Engineer;
- QA Engineer;
- Privacy, Safety и Legal;
- технических писателей и владельцев канонической документации.

...

## 2.6. Normative Force

После получения статуса `Accepted` настоящий документ становится нормативным
источником описания доменной модели Ayla.

Терминология, канонические определения и правила использования альтернативных
наименований определяются **Ayla Glossary**, который является нормативным
источником терминологического управления. Настоящий документ использует эти
определения и не переопределяет их.

Документы более низкого уровня, включая PRD, ADR, API Specifications,
Data Models, Event Specifications, Prompt Specifications и техническую
документацию, не должны переопределять канонический смысл доменных понятий,
определённых настоящим документом.

Изменение канонического значения доменного понятия допускается только
посредством внесения изменений в настоящий документ с последующим
обновлением зависимой документации.

# 3. Domain Modeling Principles

Настоящий раздел устанавливает фундаментальные принципы построения
доменной модели Ayla. Эти принципы являются обязательными для всех
репозиториев, сервисов и команд, использующих каноническую доменную модель.

## 3.1. Domain Before Implementation

Доменная модель описывает бизнес-смысл системы независимо от способа её
технической реализации.

Наличие таблицы базы данных, ORM-модели, API-контракта, UI-компонента,
LLM-ответа или внутреннего класса не означает существование отдельной
доменной сущности.

Сначала определяется доменное понятие, его смысл, жизненный цикл и
инварианты. Только после этого проектируются его технические представления.

## 3.2. Technical Representations

Доменная Entity не тождественна:

- строке базы данных;
- ORM-модели;
- API DTO;
- UI-компоненту;
- LLM Output;
- Runtime Artifact.

Все технические представления должны иметь явное сопоставление с
канонической доменной моделью.

## 3.3. Stable Identity

Каждая Entity обладает устойчивой доменной идентичностью (Identity),
которая сохраняется независимо от изменения её атрибутов.

Объекты, не обладающие собственной идентичностью, должны моделироваться
как Value Objects либо Runtime Artifacts.

## 3.4. Explicit Lifecycle

Каждая значимая доменная Entity должна иметь явно определённый жизненный
цикл (Lifecycle), включающий:

- условия создания;
- допустимые состояния;
- допустимые переходы;
- условия завершения;
- правила архивирования или удаления.

## 3.5. Domain Invariants

Каждая доменная Entity должна иметь явно определённые бизнес-инварианты.

Инварианты являются обязательными независимо от пользовательского
интерфейса, API, способа вызова или используемой технологии.

## 3.6. Aggregate Consistency

Aggregate определяет границу согласованности (Consistency Boundary).

Изменение внутреннего состояния Aggregate должно происходить через
соответствующий Aggregate Root.

Связи между различными Aggregates должны преимущественно выражаться через
устойчивые идентификаторы.

## 3.7. Facts and Inferences

Подтверждённые факты (Facts) и вычисленные предположения (Inferences)
являются различными доменными понятиями.

Inference не может использоваться как подтверждённый факт без
соответствующей процедуры валидации, происхождения (Provenance) и проверки
политик безопасности.

## 3.8. Conversation and System of Record

Conversation Runtime не является System of Record.

Информация, полученная во время диалога, становится частью постоянного
доменного состояния только после прохождения процедур валидации,
классификации, проверки Consent и записи в соответствующий
авторитетный источник данных.

## 3.9. AI and Authoritative State

LLM, AI Runtime и Recommendation Engine могут формировать предложения,
классификации и объяснения, но не изменяют авторитетное состояние
предметной области напрямую.

Любое изменение доменного состояния должно происходить через
Application Services с соблюдением доменных инвариантов.

## 3.10. One Canonical Meaning

Каждое самостоятельное доменное понятие должно иметь одно каноническое
значение и одно каноническое наименование.

Правила регистрации, классификации и использования альтернативных
наименований определяются исключительно Ayla Glossary.

## 3.11. Historical Consistency

Изменение текущего состояния системы не должно изменять исторические
бизнес-факты.

Доменная модель должна обеспечивать сохранение исторической информации,
необходимой для аудита, аналитики, разрешения споров и соблюдения
нормативных требований.

## 3.12. Commands and Domain Events

Command выражает намерение изменить состояние системы.

Domain Event фиксирует уже произошедший доменный факт.

Commands и Domain Events являются различными элементами доменной модели и
не должны использоваться как взаимозаменяемые понятия.

## 3.13. Semantic Versioning

Изменение канонической семантики доменной модели, включая изменение
значения терминов, жизненного цикла, инвариантов, границ Aggregates,
Ownership или System of Record, считается Breaking Change.

Подобные изменения требуют внесения изменений в настоящую спецификацию,
анализа влияния на зависимые системы и синхронного обновления
канонической документации.
