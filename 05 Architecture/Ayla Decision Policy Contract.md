## Назначение (Purpose)

Контракт фиксирует две вещи:

1. **Входной путь каждого сообщения** — четыре ступени из AYLA-DEC-0096 (N-1).
2. **Минимальный детерминированный выбор следующего шага** до пилота и его наблюдаемый исход — AYLA-DEC-0097 (N-2).

Цели:
- кризисная реплика получает детерминированный ответ при любом состоянии согласия и при работе оператора;
- до разрешения контекста ничего не читается из памяти и профиля;
- «что предложить дальше» решает детерминированное правило, а не модель;
- `NO_ACTION` — видимый и объяснимый результат (инв. 24);
- каждое решение объяснимо через reason, evidence и provenance (инв. 25).

Контракт **не** задаёт сложный NBA, скоринг и обучение. По AYLA-DEC-0097 это после пилота. Минимальный выбор уровнем C из AYLA-DEC-0089 не считается.

## Источник истины (Source of truth)

- **Порядок и исходы** — AYLA-DEC-0096 и AYLA-DEC-0097 в OWNER_DECISION_REGISTER. Полные формулировки — бриф `OWNER_DECISION_BRIEF_GOAL_PLAN_DIARY` ред. 2, разделы N-1 и N-2; принят владельцем целиком, CD §67.
- **Исход решения** — одна неизменяемая запись по `decision-outcome.schema.json`. Второй копии исхода с другим смыслом не заводится. Теневая строка `decision_readiness.shadow.live_turn` источником истины не является (§15).
- **Входы политики** остаются в своих источниках. Политика хранит на них ссылки (`evidence_refs`), а не копии:
  - согласия — реестр согласий бота;
  - план и действия — Personal Plan, **только актуальная версия действия** (AYLA-DEC-0092);
  - записи — каталог;
  - safety-вердикт — safety-контур.
- Порядок из ТЗ §6 «Decision Engine» (8 пунктов, включая «проверяемую нейтральную сводку») **заменён** порядком AYLA-DEC-0097. Отдельной ступени «сводка» нет.

## Сущности

**DecisionOutcome** — исход одного расчёта. Поля — те семь, что перечислены в AYLA-DEC-0097 («исход, причину, ссылки на факты, происхождение, заблокированные функции, время расчёта и версию политики»), плюс версия формы. Начальный словарь `reason_code` утверждён владельцем (решение владельца 21.09, журнал главного окна CD §72 п.22 (вне git)). Два условных поля (`clarify_question_ref`, `handoff_reason`), константа `provenance.policy` и набор значений `provenance.step` — **предложение этого контракта**, не поля и не значения DEC; утверждает владелец (ОВ-16).

| Поле | Смысл | Правило |
|---|---|---|
| `contract_version` | версия формы, major 1 (`^1\.[0-9]+$`) | неизвестная major отвергается потребителем |
| `decision_outcome` | `ACT` / `CLARIFY` / `NO_ACTION` / `BLOCKED` / `HANDOFF` | закрытый набор (AYLA-DEC-0097) |
| `reason_code` | код причины, `^[a-z_]+$` | из словаря версии `policy_version`; начальный словарь утверждён владельцем (CD §72 п.22) |
| `evidence_refs[]` | `{kind, ref}` — ссылки на факты | при `ACT` не меньше одной |
| `provenance` | `{policy, step}` | предлагается: `policy = "ayla-decision-policy"`; `step` ∈ `safety`, `explicit_intent`, `unfinished_flow`, `scheduled_action`, `plan_next_action`, `plan_proposal`, `none` (ОВ-16) |
| `blocked_capabilities[]` | функции, недоступные на момент расчёта | при `BLOCKED` не меньше одной |
| `calculated_at` | момент расчёта, date-time | обязательно |
| `policy_version` | версия правил | обязательно |
| `clarify_question_ref` | ссылка на один вопрос (не текст). **Предложение контракта** | обязателен при `CLARIFY`, запрещён иначе |
| `handoff_reason` | причина передачи оператору. **Предложение контракта** | обязателен при `HANDOFF`; вне `HANDOFF` — ОВ-14 |

**Исходы** (AYLA-DEC-0097; определения по брифу N-2):

| Исход | Когда | Что видит человек |
|---|---|---|
| `ACT` | есть допустимое полезное действие, все его входы известны | предложение действия с «почему» |
| `CLARIFY` | конкретный ответ человека способен продолжить сценарий | один вопрос; поток стоит до ответа (CD §48 п.6: «CLARIFY означает реальный вопрос пользователю, а не разрешение продолжить») |
| `NO_ACTION` | нет ни полезного действия, ни полезного вопроса | Ayla ничего не навязывает; исход наблюдаем в журнале с `reason_code` |
| `BLOCKED` | действие запрещено согласием, safety, возрастом или выключателем | объяснение, что недоступно; без обхода |
| `HANDOFF` | нужен человек-оператор | передача с указанием причины |

**Словарь `reason_code`.** Версионируется вместе с `policy_version`: любое изменение словаря меняет `policy_version` (AYLA-DEC-0097, «версию политики»). Имён кодов в AYLA-DEC-0097 и в брифе N-2 нет. **Начальный словарь утверждён владельцем как есть, дорабатывается по ходу** (решение владельца 21.09, журнал главного окна CD §72 п.22 (вне git)). Доработка — новые коды с новой `policy_version` (DP-15). Коды, упомянутые в этом контракте (`nothing_useful`, `consent_missing`, `safety_block`, `safety_handoff` и др.), — норма.

**Начальный словарь `reason_code` — утверждён владельцем (CD §72 п.22).** Утверждение касается кодов и их исходов. Столбец `provenance.step` — значения, которые контракт предлагает для поля `provenance.step`; сам состав `provenance` — предложение (ОВ-16).

| `reason_code` | Исход | Ступень (`provenance.step`, предложение — ОВ-16) | Из чего выведен |
|---|---|---|---|
| `explicit_intent` | `ACT` | `explicit_intent` | N-2 п.2 |
| `unfinished_flow` | `ACT` (предложить продолжить) | `unfinished_flow` | N-2 п.3; BOT-002 §5.6 |
| `scheduled_action_due` | `ACT` | `scheduled_action` | N-2 п.4 |
| `plan_next_action` | `ACT` | `plan_next_action` | N-2 п.5; AYLA-DEC-0092 |
| `plan_proposal_available` | `ACT` | `plan_proposal` | N-2 п.6, суженный AYLA-DEC-0091 (только при ACTIVE-цели с шаблоном) |
| `insufficient_context_question` | `CLARIFY` | ступень, на которой не хватило входа | N-2: «недостаточность данных не приравнивается к NO_ACTION» |
| `nothing_useful` | `NO_ACTION` | `none` | N-2 п.7 |
| `consent_missing` | `BLOCKED` | ступень, где запрещено | N-2 (BLOCKED — согласие) |
| `safety_block` | `BLOCKED` | `safety` | N-2 (BLOCKED — безопасность) |
| `age_block` | `BLOCKED` | ступень, где запрещено | N-2 (BLOCKED — возраст); AYLA-DEC-0100 |
| `feature_disabled` | `BLOCKED` | ступень, где запрещено | N-2 (BLOCKED — выключатель) |
| `safety_handoff` | `HANDOFF` | `safety` | N-2 (HANDOFF); N-1 ступень 1 |
| `operator_requested` | `HANDOFF` | `explicit_intent` | N-2 (HANDOFF — запрос оператора) |

Кодов сверх начального словаря нет; их добавление — доработка по ходу с новой `policy_version` (ОВ-16): safety-CLARIFY; «вход недоступен»; «сбой, который не решается автоматически» → `HANDOFF`; коды `BLOCKED` для конкретных выключателей.

**Виды `evidence_refs.kind`** и **имена `blocked_capabilities`** — словари не определены (§17, ОВ-4). В фикстурах схемы значения `plan_action_version`, `unfinished_flow`, `consent_state`, `safety_verdict`, `example_capability` — иллюстрация, не норма.

## Состояния и переходы

**Входной путь сообщения** (AYLA-DEC-0096). Ступени строго по порядку:

1. **Минимальный входной детектор опасности.**
   - Читает только текущее сообщение, без памяти и профиля.
   - Кризис или неотложка → детерминированный ответ **всегда**: при согласии, не данном или отозванном, и при работе оператора (handoff).
   - Про вложения см. §17, ОВ-6.
2. **Consent и context authorization** — какой контекст разрешено читать для этой цели (purpose).
3. **Расширенная safety** с разрешённым контекстом. Удержанный S1-вердикт (DRF-2040) живёт здесь, по брифу N-1.
4. **Функции.**

Фраза Journey «consent/privacy → safety» относится к составлению рекомендаций из персонального контекста и действует внутри ступеней 2–4 (AYLA-DEC-0096; поправка Journey v1.3).

**Выбор следующего шага** (AYLA-DEC-0097). Первая сработавшая ступень даёт исход:

1. safety (результат ступеней 1 и 3 входного пути);
2. явное намерение человека — если оно есть, выполняется оно; ступени 3–7 не применяются (BOT-002 MM-D5);
3. незавершённый сценарий — предложить, не навязывать. Предложение само не меняет Current Focus (BOT-002 §5.6);
4. подтверждённое действие на текущее время. Для действий плана «текущее время» — слот дня (`утро` / `день` / `вечер`) и день недели; точного часа до пилота нет (решение владельца 21.09, журнал главного окна CD §72 п.18 (вне git); [[Ayla Personal Plan Contract]] I-21);
5. следующее действие активного плана — только актуальная версия действия (AYLA-DEC-0092);
6. предложение собрать план — только если плана нет и есть ACTIVE-цель с шаблоном (AYLA-DEC-0091; решение владельца 21.09, CD §71 п.3: «Без цели Ayla не предлагает и не создаёт план по своей инициативе. Такой план может собрать только сам пользователь. Это правило P-1 имеет приоритет»). Бриф N-2 п.6 («цель или явный запрос») шире; AYLA-DEC-0091 его сужает;
7. иначе `NO_ACTION`.

**Явный запрос плана без цели** — это ступень 2 (явное намерение), до ступени 6 он не доходит. Он открывает ручной конструктор плана (`ComposeManual`, [[Ayla Personal Plan Contract]]), а не предложение Ayla.

**Где применяются ступени 3–7:** только без явного намерения — приветствие, «что дальше?», карточка «Сегодня», завершение действия.

**Отдельной ступени consent в выборе нет:** она уже стоит на ступени 2 входного пути, а каждый кандидат несёт `blocked_capabilities` (бриф N-2).

**Состояния исхода.** DecisionOutcome неизменяем, переходов у записи нет. Новый расчёт — новая запись. Смысловые состояния потока:

| После исхода | Что дальше |
|---|---|
| `CLARIFY` | Поток стоит до ответа на вопрос. Ответ → новый расчёт. Явное новое намерение выигрывает (MM-D5). |
| `BLOCKED` | Меняется только после изменения входа: согласие дано, флаг включён. Ayla не обходит блок. |
| `HANDOFF` | Работу ведёт оператор. Ступень 1 входного пути действует и во время handoff. |
| `ACT` / `NO_ACTION` | Терминальные для расчёта. |

Имена рабочие; окончательные — при реализации (§17, ОВ-8).

| Команда | Кто вызывает | Результат |

  - Полезная нагрузка — поля DecisionOutcome по схеме.

## Входы и выходы

**Входы расчёта.** Все читаются только после ступени 2 входного пути и только в разрешённом объёме:

- safety-вердикт ступеней 1 и 3; признак handoff;
- явное намерение текущего хода (как определяется — ОВ-2);
- незавершённый сценарий (Task вне Current Focus, BOT-002);
- подтверждённые действия со временем: записи; действия плана с назначенным временем — слот дня (`утро` / `день` / `вечер`) + дни недели (CD §72 п.18; Personal Plan Contract I-21);
- активный план и актуальные версии его действий (AYLA-DEC-0092);
- наличие плана и ACTIVE-цели с шаблоном — основание для предложения на ступени 6 (AYLA-DEC-0091; CD §71 п.3). Goal для работы Ayla в целом необязательна (AYLA-DEC-0087), но без неё предложения плана нет;
- состояние согласий, выключателей, возрастной статус (AYLA-DEC-0100: наружу только статус и возраст в годах).

**Выход** — DecisionOutcome по `decision-outcome.schema.json`:
- `additionalProperties: false`;
- `contract_version` — `^1\.[0-9]+$`: любая minor major-версии 1 проходит схему, другая major отвергается;
- условные правила: `CLARIFY` ⇒ `clarify_question_ref`, иначе оно запрещено; `HANDOFF` ⇒ `handoff_reason`; `ACT` ⇒ `evidence_refs` ≥ 1; `BLOCKED` ⇒ `blocked_capabilities` ≥ 1 (условные поля — предложение, ОВ-16).

**Версии.**
- `contract_version`: additive-поле — minor; удаление, переименование, смена семантики — major и change control. Так же устроено правило `contract_version` в Intent Model v1.0.
- Потребитель **отвергает неизвестную major** (ТЗ §10, contract test «unknown major rejection») и принимает известную major с любой minor. Схема выражает это шаблоном `^1\.[0-9]+$`, а не константой.
- Оговорка: в `intent-output.schema.json` KB это правило буквально не записано. Там — только правило нумерации. Отказ на неизвестной major здесь записан явно.

## Инварианты

- **DP-1.** Ступень 1 входного пути выполняется первой для каждого входящего сообщения:
  - раньше молчания при handoff;
  - раньше проверки согласия;
  - без чтения памяти и профиля.

  Кризис и неотложка получают детерминированный ответ всегда. — AYLA-DEC-0096; инв. 22.
- **DP-2.** До ступени 2 ни одно чтение памяти или профиля не выполняется. — AYLA-DEC-0096.
- **DP-3.** Safety имеет приоритет над Goal, планом, рекомендацией и proactive. — AYLA-DEC-0096, AYLA-DEC-0097 (ступень 1); инв. 22.
- **DP-4.** Явное намерение человека выполняется. Ступени 3–7 при нём не применяются. — AYLA-DEC-0097; BOT-002 MM-D5.
- **DP-5.** Незавершённый сценарий только предлагается, не навязывается. — AYLA-DEC-0097; BOT-002 §5.6.
- **DP-6.** Исход выбирает детерминированное правило. Модель только формулирует выбранное. Модель не создаёт обязательств пользователя и не меняет план. — AYLA-DEC-0097, AYLA-DEC-0045; инв. 7, 8.
- **DP-7.** `ACT` на ступенях 3–6 — **предложение**. Оно не равно подтверждённому действию и ничего не создаёт без подтверждения человека. — AYLA-DEC-0097 («предложить»); Journey «Recommendation никогда не выполняет side effect автоматически»; инв. 9.
- **DP-8.** Набор исходов закрыт: `ACT`, `CLARIFY`, `NO_ACTION`, `BLOCKED`, `HANDOFF`. — AYLA-DEC-0097.
- **DP-9.** Недостаточность данных не приравнивается к `NO_ACTION`:
  - если конкретный ответ человека способен продолжить сценарий — `CLARIFY`;
  - иначе — `NO_ACTION` или `BLOCKED` по причине.

  `NO_ACTION` никогда не подменяет вопрос, который нужно задать. `UNKNOWN`-вход не маскируется умолчанием. — AYLA-DEC-0097; инв. 5.
- **DP-10.** `NO_ACTION` — валидный, наблюдаемый результат с `reason_code`. — AYLA-DEC-0097, AYLA-DEC-0045; инв. 24.
- **DP-11.** Каждый исход несёт `decision_outcome`, `reason_code`, `evidence_refs`, `provenance`, `blocked_capabilities`, `calculated_at`, `policy_version`. `ACT` без `evidence_refs` недопустим. — AYLA-DEC-0097; инв. 25; Конституция ст. VII.
- **DP-12.** `CLARIFY` — ровно один вопрос. Поток стоит до ответа. — AYLA-DEC-0097; CD §48 п.6.
- **DP-13.** `BLOCKED` объясняет, что недоступно, и не предлагает обхода. — AYLA-DEC-0097.
- **DP-14.** В расчёте участвует только актуальная версия действия плана. Заменённые и удалённые версии не участвуют. — AYLA-DEC-0092.
- **DP-15.** Словарь `reason_code` закрыт и меняется только вместе с `policy_version`. Начальный словарь утверждён владельцем как есть, доработка — по ходу, каждой новой `policy_version` («Сущности», таблица начального словаря). — AYLA-DEC-0097 («версию политики»); решение владельца 21.09, журнал главного окна CD §72 п.22 (вне git).
- **DP-16.** Proactive-гейт учитывает активный safety-вердикт и handoff: при них бот первым не пишет. — инв. 22; бриф T-7 (DRF-2213). Точная длительность «активного» вердикта — ОВ-7.
- **DP-17.** Без ACTIVE-цели Ayla не предлагает и не создаёт план по своей инициативе; ступень 6 срабатывает только при ACTIVE-цели с шаблоном. Явный запрос плана без цели — ступень 2 → ручной конструктор. — AYLA-DEC-0091; решение владельца 21.09 (CD §71 п.3).
- **DP-18.** Кризисная реплика получает готовый детерминированный ответ **всегда**, в том числе при сбое систем, **и** оператору уходит сигнал о кризисном ответе бота — как CD §72 п.1а: салонный бот — без текста клиента; общий бот — в очередь операторов платформы. Сигнал — не передача разговора оператору: вопрос 21 (`docs/OWNER_QUESTIONS_2026-09-21_EVENING.md`, вне git) противопоставлял «готовый ответ + передать разговор оператору», выбран «готовый ответ + сигнал». — AYLA-DEC-0096; решение владельца 21.09, журнал главного окна CD §72 п.21 (вне git); инв. 22.

## Согласие (Consent)

- Ступень 1 согласия не требует. Обработка текущего сообщения в сессии согласия не требует — CSR v1.4 §3, CDP-07; бриф N-1 «Состояние».
- Ступень 2 определяет разрешённый контекст по цели (purpose) по [[Consent Scope Registry]] и [[Ayla Context Resolution Contract]]. Всё, что запрещено согласием, даёт кандидату `blocked_capabilities` и при выборе этого действия — `BLOCKED` / `consent_missing`.
- Отзыв согласия закрывает дальнейшее чтение соответствующих входов. Следующий расчёт видит отзыв (E2E 20). Runtime: согласие `PERSONAL_DATA` на показе своих записей и в онбординге читается по человеку — по всем его оболочкам, последний отзыв закрывает — так (слито #1957, `eec1ded5`, DRF-2230; `bot@808ca79d:apps/consent/services.py:437-466`). Прочие гейты читают согласие по строке; какой из двух способов обязателен для ступени 2 — решением не задано.
- Proactive-уведомления — только по opt-in (AYLA-DEC-0087). Требование user-initiated для рекомендаций услуг остаётся (запись к AYLA-DEC-0046).
- Нового scope согласия контракт не вводит. Правовое основание записи журнала решений для человека без согласия — ОВ-5.

## Приватность (Privacy)

- **Журнал решений — персональные данные** (бриф N-2 «Данные»). Правила:
  - Журнал входит в **экспорт** персональных данных.
  - Журнал стирается **«Забудь всё»** в обоих путях — бот и приложение. По образцу AYLA-DEC-0101: команда обещает забыть всё, код приводится к тексту команды. Инв. 21.
  - Строка «журнал решений N-2» добавляется в [[Data Inventory Matrix]] (бриф, Итог 3 п.12).
  - Покрытие export/forget — поправка к [[AMD-001 C5 Pilot Personal Context Export-Forget Contract]]. Путь исполнения «Забудь всё» — DRF-2214.
- **Минимизация.**
  - В исходе и в событии — только коды и ссылки.
  - Текст сообщения, значения питания, тела и здоровья, аллергии в DecisionOutcome не пишутся.
  - Аллергии и флаги здоровья во внешнюю модель не уходят (AYLA-DEC-0098, AYLA-DEC-0100). Формулировка исхода моделью подчиняется тем же запретам.
- **Место хранения** не определено (ОВ-1). Срок хранения не определён (ОВ-9).

## Безопасность (Safety)

- Ступень 1 — минимальный детерминированный детектор: без памяти, без профиля, без модели. Кризис и неотложка → детерминированный ответ всегда, включая handoff (AYLA-DEC-0096).
- Ступень 3 — расширенная оценка с разрешённым контекстом. Удержание S1-вердикта между ходами (DRF-2040) — здесь.
- Safety-исходы выбора:
  - запрет → `BLOCKED` / `safety_block`;
  - нужен человек → `HANDOFF` / `safety_handoff`;
  - нужен ответ человека → `CLARIFY`. Кода причины в начальном словаре нет — доработка по ходу (ОВ-16).
- **Кризис** (CD §72 п.21, DP-18): готовый детерминированный ответ всегда, в том числе при сбое систем, плюс сигнал оператору по форме CD §72 п.1а (салонный бот — без текста клиента; общий бот — очередь операторов платформы). Разговор оператору не передаётся.
- Proactive молчит при активном safety-вердикте и при handoff (DP-16, DRF-2213).
- Согласовать с DRF-2213 / DRF-2000 (ayla-ee, путь исполнения safety) и DRF-1993 (S1/F0 PASS, CD §63). Этот контракт не определяет клинические правила детекторов.

## Наблюдаемость (Observability)

- Каждый расчёт даёт одну запись журнала и событие `decision.evaluated` с полным DecisionOutcome.
- Считаемые срезы (без новых порогов):
  - распределение `decision_outcome` × `reason_code` × `policy_version`;
  - доля `NO_ACTION`;
  - `CLARIFY` без последующего ответа;
  - `BLOCKED` по `blocked_capabilities`.
- Ступень 1 наблюдаема отдельно: сработал ли детектор при handoff и при отсутствующем согласии. Это прямая проверка DP-1.
- Строка тени `decision_readiness.shadow.live_turn` (`bot:apps/orchestrator/dr_shadow.py:55`) — наблюдение тени, не журнал решений.

## Поведение при сбоях (Failure behavior)

- **Ступень 1 недоступна или сломана.** Сбой не считается «безопасно». Fail-closed: отсутствие safety-вердикта не превращается в подтверждение. Та же норма в теневой политике: `bot:apps/orchestrator/decision_policy.py:127-130`, `:226-231`. Какой именно исход показывать человеку — ОВ-10.
- **Недоступен вход ступеней 3–6** (план, записи, согласия). Недоступный вход не выдаётся за отсутствие действия. Исход — `CLARIFY`, если вход можно спросить; иначе `NO_ACTION` или `BLOCKED` по причине (DP-9). Кода «вход недоступен» в начальном словаре нет — доработка по ходу (ОВ-16).
- **Сбой модели при формулировке.** Исход не меняется. Какой текст показать — ОВ-10. Модель не может «исправить» исход.
- **Сбой записи в журнал.** Требование: исход без записи не считается наблюдаемым (инв. 24). Поведение хода при сбое записи — ОВ-10.
- **Неизвестная major `contract_version` или неизвестный `reason_code` для данной `policy_version`** — потребитель отвергает запись.

- **ОВ-14. `handoff_reason` вне `HANDOFF`.** Решение требует его только при `HANDOFF`. Запрещать ли его при других исходах (как `clarify_question_ref`)? Схема сейчас не запрещает.
- **ОВ-15. Соответствие `decision_outcome` и `ResultStatus` каталога.** Например: `SAFETY_BOUNDARY` → `BLOCKED` или `HANDOFF`? `INSUFFICIENT_CONTEXT` → `CLARIFY`? Решается в поправке Recommendation Contract, здесь не вводится.
- **ОВ-16. Остаток ОВ-3 после CD §72 п.22.** Владелец утвердил начальный словарь `reason_code` («словарь причин решений»). Не утверждены и остаются предложением контракта:
  - `provenance.policy = "ayla-decision-policy"` и набор значений `provenance.step` (столбец таблицы начального словаря);
  - поля `clarify_question_ref` (обязателен при `CLARIFY`, запрещён иначе) и `handoff_reason` (обязателен при `HANDOFF`). Схема держит эту форму с пометкой «proposed».

  Коды сверх начального словаря — доработка по ходу, каждая с новой `policy_version`: safety-CLARIFY; «вход недоступен»; «сбой, который не решается автоматически» → `HANDOFF`; коды `BLOCKED` для конкретных выключателей.

## Критерии приёмки

- **КП-1** (E2E 19). Кризисная реплика:
  - при активном handoff получает детерминированный кризисный ответ на **всех** путях: глобальный MAX, потенантный MAX, Telegram;
  - при не данном и при отозванном согласии — тоже.
- **КП-2** (E2E 19). Запрещённое safety действие даёт `BLOCKED` / `safety_block` с непустыми `blocked_capabilities`. Обхода в ответе нет.
- **КП-3** (E2E 22). Каждый исход проходит `decision-outcome.schema.json`. У `ACT` есть `evidence_refs` (≥ 1), `reason_code`, `provenance.step`, `calculated_at`, `policy_version`.
- **КП-4** (E2E 23). При отсутствии полезного действия и вопроса — `NO_ACTION` / `nothing_useful`, `provenance.step = none`. Запись видна в журнале.
- **КП-5** (unit «decision priority»). При явном намерении ступени 3–7 не выполняются. При одновременном наличии незавершённого сценария и действия плана выигрывает сценарий, и он **предлагается**: Current Focus не меняется.
- **КП-6** (unit «`no_action`»). При нехватке входа, который человек может дать, исход — `CLARIFY` с одним `clarify_question_ref`, а не `NO_ACTION`.
- **КП-7** (E2E 20). После отзыва согласия следующий расчёт не читает закрытый вход. Действие, которому он нужен, даёт `BLOCKED` / `consent_missing`.
- **КП-8** (contract tests). Схема:
  - отвергает документ с `contract_version` другой major;
  - отвергает лишнее поле;
  - отвергает `reason_code` не в форме `^[a-z_]+$`.

  Потребитель отвергает `reason_code` вне словаря своей `policy_version`.
- **КП-9** (E2E 24; integration «Safety + Decision Engine»). Proactive не отправляется при активном safety-вердикте и при handoff.
- **КП-10** (E2E 21). «Забудь всё» стирает журнал решений. Экспорт его отдаёт.
- **КП-11.** В расчёте участвует только актуальная версия действия плана (AYLA-DEC-0092). Изменённое действие не даёт двух кандидатов.
- **КП-12.** Фикстуры `schemas/fixtures/decision-outcome/`: `valid_*.json` проходят, `invalid_*.json` отвергаются. Среди них: `valid_minor-1-1.json` (`contract_version` "1.1" проходит), `invalid_major-2-0.json` ("2.0" отвергается), `valid_handoff-safety.json`, `invalid_clarify-ref-outside-clarify.json`. Проверено `jsonschema` 4.25 (Draft 2020-12): 6 из 6 valid проходят, 6 из 6 invalid отвергаются.
- **КП-13.** Без ACTIVE-цели расчёт не даёт `ACT` со `provenance.step = plan_proposal`. Явный запрос плана без цели обрабатывается ступенью 2 и открывает ручной конструктор (DP-17).
- **КП-14** (E2E 19). Кризисная реплика, в том числе при сбое систем, получает готовый детерминированный ответ, и оператору уходит сигнал по форме CD §72 п.1а (салонный бот — без текста клиента; общий бот — очередь операторов платформы); разговор оператору не передаётся (DP-18).

## Влияние на миграции (Migration impact)

- **Бот.**
  - Новый детерминированный модуль выбора на базе `decision_policy.py`.

  - Хранилище журнала — если ОВ-1 решится в пользу каталога.
- **Тень.** `decision-policy-v1-shadow` и `DRE_SHADOW_ENABLED` не удаляются этим контрактом. Судьба — ОВ-12.
- **KB (поправки — отдельные документы):**
