# 1. Journey Operating Model

## 1.1 Core Principle

**Ayla превращает неопределённость человека в безопасный, осознанный и выполнимый следующий шаг.**

Это не просто "запись к мастеру". Это:
- Понимание, что происходит (Intent Understanding)
- Сбор достаточного контекста (Discovery)
- Выбор безопасного пути (Recommendation)
- Помощь в выполнении (Execution)
- Обучение на результате (Feedback)

**Ключевая capability-модель:** Ayla объединяет contextual understanding,
governed memory, recommendation и execution в одном контролируемом Journey.
Это описание требуемых возможностей Ayla, а не утверждение о возможностях
конкретных сторонних продуктов.

## 1.2 User Value Loop
Неопределённость
↓
Понимание ситуации (Ayla помогает сформулировать)
↓
Выбор безопасного следующего шага (Ayla рекомендует)
↓
Реальное действие (Ayla организует)
↓
Получение результата (пользователь оценивает)
↓
Обучение (Ayla запоминает и улучшает)
↓
Следующий цикл (с меньшим трением)


**Метрика цикла:** End-to-End Journey Completion Rate — доля eligible Journey,
которые прошли требуемые для своего Action Class состояния и завершились
подтверждённым результатом.

## 1.3 Ayla Responsibility

**Ayla отвечает за:**
- Понимание намерения (даже из хаотичного сообщения)
- Сбор достаточного контекста (без превращения в анкету)
- Предложение безопасного следующего шага (с объяснением)
- Помощь в выполнении (запись, план, информация)
- Обучение на результате (обновление модели)

**Ayla НЕ отвечает за:**
- Профессиональную квалификацию специалиста (это ответственность специалиста)
- Медицинский результат (это ответственность врача)
- Личный выбор пользователя (Ayla предлагает, пользователь решает)

# 2. User Mental Model

## User Problem

**Основная проблема:** Человек не знает, с чего начать заботу о себе. Он тонет в информации, каталогах и противоречивых советах.

**Без Ayla:**
- Сам ищет информацию
- Сам сравнивает специалистов
- Сам координирует действия
- Сам принимает решения
- Сам отслеживает прогресс

**С Ayla:**
- Ayla помогает сформулировать проблему
- Ayla собирает контекст
- Ayla предлагает следующий шаг
- Ayla организует действие
- Ayla отслеживает прогресс

## User Expectations

**Пользователь ожидает:**
- Быстрого понимания (не нужно объяснять дважды)
- Конкретного предложения (не абстрактные советы)
- Безопасности (не навреди)
- Прозрачности (почему именно это?)
- Контроля (я могу изменить, удалить, отказаться)

**Пользователь НЕ ожидает:**
- Длинной анкеты при первом контакте
- Давления ("купи сейчас!")
- Медицинских диагнозов от AI
- Скрытого сбора данных
- Навязывания ненужных услуг

## User Fears

**Основные страхи:**
- "AI меня не поймёт" (риск неверной рекомендации)
- "AI будет давить" (риск манипуляции)
- "AI узнает слишком много" (риск приватности)
- "AI ошибётся, и я пострадал" (риск безопасности)
- "AI будет спамить" (риск навязчивости)

**Как Ayla снижает страхи:**
- Объяснимость (почему именно это?)
- Прозрачность памяти (что сохранено, на каком основании и как изменить)
- Раздельные recommendation/proactivity gates
- Границы компетенции (направляю к специалисту, если нужно)
- Право на вето (пользователь может отказаться)

## Trust Formation

**Доверие формируется через:**
1. **Первый WOW:** Ayla сформулировала проблему лучше, чем я сам
2. **Первый результат:** Ayla помогла выполнить действие и получить пользу
3. **Прозрачность:** Ayla показывает, что сохранено и на каком основании, и
   позволяет изменить
4. **Надёжность:** Ayla не давит, не навязывает, уважает выбор
5. **Последовательность:** Ayla помнит контекст и не начинает с нуля

**Доверие разрушается через:**
- Навязывание (давление, FOMO)
- Непрозрачность (скрытый сбор данных)
- Ошибки без исправления (Ayla не признаёт ошибку)
- Нарушение границ (медицинские советы без квалификации)
- Спам (проактивность без уместности)

# 3. Journey Overview

## Journey States

Journey содержит 9 состояний. S0 является pre-interaction acquisition state, а
не состоянием активной пользовательской сессии. S1-S7 описывают основной цикл
ценности. S8 является защитным состоянием и может быть вызвано из любого
активного состояния.

| Состояние | Описание | Длительность |
|---|---|---|
| **S0: Acquisition** | Пользователь узнаёт о Ayla через триггер | Мгновенно |
| **S1: First Contact** | Первое сообщение в MAX Bot | 0-2 мин |
| **S2: Discovery** | Сбор минимально достаточного контекста | 2-5 мин |
| **S3: Intent Understanding** | Ayla понимает намерение | 1-5 мин |
| **S4: Recommendation** | Ayla предлагает следующий шаг | 1-5 мин |
| **S5: Execution** | Пользователь выполняет действие | 10-15 мин |
| **S6: Feedback** | Пользователь оценивает результат | После действия |
| **S7: Long-term** | Формирование привычки | 7-30 дней |
| **S8: Boundary Handling** | Ayla не может безопасно продолжить текущий путь и обозначает границу | Немедленно |

Длительность в таблице — ориентировочная продолжительность самого состояния,
а не cumulative SLA. First Value должен возникать в S2 или S3 и не обязан быть
Recommendation: им может быть полезная переформулировка, выявленное ограничение
или безопасный preliminary insight.

## State Transitions
S0 → S1: Пользователь открывает MAX Bot
S1 → S2: Пользователь выбирает категорию или пишет свободный запрос
S2 → S3: Ayla собрала достаточный контекст (Context Sufficiency Gate)
S3 → S4: Ayla сформулировала намерение и проверила безопасность
S4 → S5: Пользователь выбрал действие (запись, план, информация)
S5 → S6: Действие выполнено (запись состоялась, план начат)
S5 → SR: Execution завершился ошибкой и требует Recovery
S6 → S7: Пользователь получил пользу и вернулся
S7 → S2: Пользователь вернулся с новым намерением
S1-S7 → S8: Обнаружен запрос вне компетенции или safety-critical риск
S8 → S2: Риск снят, пользователь сформулировал безопасное новое намерение
S8 → S4: Разрешена только безопасная рекомендация или обращение к квалифицированному специалисту
S8 → Exit: Ayla прекращает предметную рекомендацию, если безопасного продолжения нет

**Обратные переходы:**
- S4 → S3: Пользователь уточняет контекст ("а можно без тренера?")
- S5 → S4: Пользователь передумал ("давай другую опцию")
- S6 → S4: Результат не удовлетворил ("не подошло, давай другое")

### Dynamic Intent Transition

Journey не считается строго линейным. Пользователь может менять намерение в
рамках одной сессии. Ayla должна обнаруживать сдвиг и запускать Incremental
Discovery с учётом нового контекста.

**Initial Discovery** — первичный сбор минимально достаточного контекста.

**Incremental Discovery** — дозаполнение или пересмотр только тех Context Slot,
которые затронуты новым Intent.

Триггеры сдвига:
- Пользователь явно меняет тему ("а вообще-то у меня болит плечо")
- Новый сигнал противоречит текущему Intent
- Пользователь задаёт вопрос из другой предметной области

Действие Ayla:
1. Фиксирует Intent Shift
2. Передаёт в Incremental Discovery только разрешённый к повторному
   использованию Context
3. Перезапускает Safety Re-evaluation для нового Intent
4. Обновляет Recommendation Layer
5. Не продолжает execution по старому Intent без нового подтверждения пользователя

Ранее подтверждённый Context Slot повторно не спрашивается, только если он
релевантен новому Intent, совместим с новой purpose, не устарел и не
противоречит новому сигналу. Нерелевантный, конфликтующий или purpose-incompatible
Context не переносится автоматически.

Пример:
Пользователь: "Хочу массаж"
Ayla: "Расскажи немного"
Пользователь: "У меня вообще-то болит плечо после тренировки"

→ Intent Shift: "массаж" → "восстановление после травмы"
→ Safety Re-evaluation: высокий риск? нужен специалист?
→ Новый путь: не каталог массажистов, а триаж к специалисту

# 4. Stage Specifications

## Stage 0 — Acquisition Trigger

### User State
Пользователь узнаёт о Ayla через один из триггеров:
- **Болевой триггер:** "Устала после работы, не знаю как расслабиться" → увидела пост "Ayla подберёт, что тебе нужно за 2 минуты"
- **Социальный триггер:** Подруга прислала "Записалась через Ayla, она подобрала идеального мастера"
- **Контекстный триггер:** QR в салоне "В следующий раз Ayla подберёт мастера под твои предпочтения"
- **Рекламный триггер:** Таргетированная реклама "Не знаешь, с чего начать? Ayla поможет"

### Intent
Пользователь ещё не сформулировал намерение. Он в состоянии "неопределённости" или "боли".

### Channel
- MAX Bot (primary)
- Mini App (secondary, через deep link)
- Web (future)

### Ayla Responsibility
- Резонировать с триггером (если известен)
- Использовать универсальный вход (если триггер неизвестен)
- Не начинать с анкеты или продажи

### Success Criteria
- Пользователь открыл MAX Bot
- Пользователь увидел первое сообщение Ayla
- Пользователь начал диалог (выбрал категорию или написал запрос)

**Метрика:** Acquisition Rate — доля пользователей, которые открыли бот и начали диалог.

## Stage 1 — First Contact

### Entry Points
1. **MAX Bot DM:** Пользователь открывает бот и видит приветствие
2. **Mini App deep link:** Пользователь переходит из рекламы/QR в Mini App
3. **Re-engagement:** Пользователь возвращается после паузы

### First Message (MAX Bot)
Привет! Я Ayla.
Помогу разобраться, что тебе сейчас нужно,
и подобрать следующий шаг.
Что привело тебя?
[Я устала и хочу восстановиться]
[Хочу изменить тело или питание]
[Хочу начать заниматься]
[Что-то беспокоит]
[Не знаю, с чего начать — помоги]
Или напиши своими словами 👇

### Allowed Behavior
- Предложить категории (состояния, не цели)
- Дать возможность свободного ввода
- Не начинать с анкеты
- Не продавать
- Не объяснять, "что такое Ayla"

### Forbidden Behavior
- ❌ Длинное описание возможностей
- ❌ Запрос имени, возраста, веса при первом контакте
- ❌ Давление ("запишись сейчас!")
- ❌ Медицинские термины без объяснения

### WOW Preparation
WOW-момент готовится на Stage 3 (Intent Understanding), но закладывается здесь:
- Ayla не спрашивает "что ты хочешь?" (абстрактно)
- Ayla спрашивает "что привело тебя?" (конкретно, эмоционально)
- Ayla даёт возможность свободного ввода (не ограничивает кнопками)

### Success Criteria
- Пользователь выбрал категорию или написал свободный запрос
- Пользователь не закрыл бот после первого сообщения

**Метрика:** First Contact Completion Rate — доля пользователей, которые завершили Stage 1.

## Stage 2 — Discovery

### Context Collection
Ayla собирает минимально достаточный контекст через 3-5 вопросов.

**Обязательные слоты:**
1. **State:** Что происходит сейчас? (усталость, боль, недовольство)
2. **Goal:** Чего хочет достичь? (похудеть, восстановиться, начать заниматься)
3. **Constraints:** Ограничения? (аллергии, травмы, время, бюджет)
4. **Preferences:** Предпочтения? (время, формат, расположение)

**Опциональные слоты (если уместно):**
- История (что уже пробовал?)
- Срочность (когда нужно?)
- Бюджет (сколько готов потратить?)

### Context Sufficiency Gate

**Правило:** Context Sufficiency определяется не количеством заполненных
слотов, а обязательным набором данных для конкретных Intent Type, Action Class
и Risk Level.

Переход из S2 всегда ведёт в S3. Запрос «просто запиши меня» и отказ отвечать
на дополнительные вопросы включают fast path, но не обходят Intent
Understanding, safety evaluation и явное подтверждение действия:

S2 Minimal Discovery → S3 Lightweight Intent Confirmation →
S4 Direct Booking Recommendation → S5 Execution.

Если обязательного контекста для выбранного действия недостаточно, Ayla
обозначает неопределённость, задаёт минимально необходимый вопрос либо
применяет Boundary Handling. Она не выполняет действие на основании
произвольного количества заполненных слотов.

### Maximum Questions
**Правило:** Не более 5 вопросов за всю сессию Discovery.

**Почему:**
- Каждый вопрос расходует доверие (Конституция Ст. VI.1)
- Пользователь пришёл решить проблему, не заполнять анкету
- Если нужно больше 5 вопросов → проблема в формулировке вопросов

### Handling Incomplete Answers

**Сценарий 1:** Пользователь отвечает односложно ("нормально", "не знаю")
- **Действие:** Переформулировать вопрос с примерами
- **Пример:** "Расскажи, что сейчас сложнее всего? Например: не хватает времени, не знаешь с чего начать, сложно держать режим. Или опиши своими словами."

**Сценарий 2:** Пользователь отказывается отвечать
- **Действие:** Перейти к Stage 3 с тем, что есть + обозначить неопределённость
- **Пример:** "Поняла. Судя по тому, что ты рассказал, я бы предложила... Но если хочешь более точную рекомендацию, могу уточнить пару деталей."

**Сценарий 3:** Пользователь даёт противоречивые ответы
- **Действие:** Уточнить приоритет
- **Пример:** "Ты сказал, что хочешь похудеть, но также упомянул, что сейчас мало времени. Что для тебя сейчас важнее: быстрый результат или постепенные изменения?"

### Success Criteria
- Ayla собрала обязательный набор Context для конкретных Intent Type,
  Action Class и Risk Level
- Пользователь не закрыл бот во время Discovery
- User подтвердил формулировку Intent либо явно завершил Discovery

**Метрика:** Discovery Completion Rate — доля пользователей, которые завершили Stage 2.

## Stage 3 — Intent Understanding

### Query vs Intent

**Query:** То, что пользователь написал ("Хочу массаж")  
**Intent:** То, что пользователь хочет достичь ("восстановиться после нагрузки")

**Примеры:**

| Query | Intent |
|---|---|
| "Хочу массаж" | Восстановиться после нагрузки |
| "Хочу похудеть" | Улучшить форму тела |
| "Болит спина" | Снять напряжение / решить проблему |
| "Хочу записаться к Анне" | Получить конкретную услугу у доверенного мастера |

### Intent Extraction

**Архитектура:**
    User Message
↓
LLM understands intent + extracts slots
↓
Intent Type Classifier (определяет коммуникативный тип намерения)
↓
Context Sufficiency Check (достаточно ли данных?)
↓
Safety Constraints (есть ли риски?)
↓
Memory Lookup (что уже знаем о пользователе?)
↓
Recommendation Engine (что предложить?)

### Intent Type

Коммуникативный тип текущего Intent:

- `goal`;
- `action`;
- `information`;
- `management`;
- `feedback`;
- `correction`.

### Goal Category

Предметная категория Goal:

- `recovery`;
- `appearance`;
- `nutrition`;
- `fitness`;
- `self-care`;
- `booking`.

### Product Lifecycle Goal

Категория продуктового пути, не являющаяся Intent Type:

- `acquisition`;
- `activation`;
- `retention`.

### Confidence

**Правило:** Ayla показывает уверенность в понимании намерения через язык:
- **Высокая уверенность (>0.8):** "Похоже, тебе сейчас важно восстановиться..."
- **Средняя уверенность (0.5-0.8):** "Возможно, ты хочешь..."
- **Низкая уверенность (<0.5):** "Я не уверена, правильно ли поняла. Уточни, пожалуйста..."

### Safety Check

**Правило:** Перед переходом к Stage 4 Ayla проверяет safety constraints:
- Есть ли red-zone факты (аллергии, противопоказания)?
- Есть ли конфликт целей (например, "быстро похудеть" + "беременность")?
- Есть ли риск вреда (например, "жёсткий массаж" + "травма спины")?

**Если риск обнаружен:**
- при высоком риске или competence boundary Ayla переходит в S8;
- Ayla не подтверждает и не продолжает небезопасный путь;
- безопасная альтернатива или направление к квалифицированному специалисту
  предлагаются только после Boundary Handling.

### WOW Moment

**WOW = "Она сформулировала мою проблему лучше, чем я сам"**

**Пример:**
Пользователь: "Хочу похудеть."
Ayla уточнила предыдущий опыт и ограничения.
Пользователь: "Начинаю, но через неделю бросаю."
Ayla: "Похоже, ключевая трудность — не выбрать жёсткую диету, а удержать
выполнимый режим. Давай сначала выберем безопасный небольшой шаг."

**Почему это WOW:**
- Ayla не просто приняла запрос ("хочу похудеть" → "вот диета")
- Ayla поняла контекст (сложно удерживать режим)
- Ayla предложила безопасное направление без неподтверждённых выводов

### Success Criteria
- Ayla правильно определила намерение (подтверждено пользователем)
- Ayla проверила safety constraints
- Пользователь согласился с формулировкой намерения

**Метрика:** Intent Recognition Accuracy — доля правильно распознанных намерений.

---

## Stage 4 — Recommendation Layer

### Next Best Action Framework

**Правило:** Ayla предлагает **лучший первый шаг**, а не "одно правильное решение".

**Структура рекомендации:**

1. **Что я поняла:**
   - "Ты хочешь снизить вес без жёстких ограничений"
   - "Ты давно не тренировалась"
   - "Тебе важно не перегореть"

2. **Почему я предлагаю это:**
   - "Интенсивные нагрузки сейчас могут демотивировать"
   - "Мягкий старт повышает вероятность, что ты продолжишь"

3. **Риски:**
   - "Если сразу начать с жёсткой диеты, есть риск срыва"

4. **Следующий шаг:**
   - "Консультация тренера для мягкого старта"
   - "Или план питания на 7 дней"

### Decision Matrix

**Правило:** Ayla выбирает между тремя путями:

| Условие | Действие | Пример |
|---|---|---|
| Низкий риск + есть простые действия | Предложить самостоятельно | "Попробуй 3 упражнения по 10 минут в день" |
| Нужна квалификация | Предложить специалиста | "Записаться к тренеру" |
| Нет контекста / высокий риск | Пауза + уточнение | "Давай сначала разберёмся..." |

**Матрица решений:**
IF risk == low AND simple_actions_available:
→ Propose self_action
ELIF qualification_required:
→ Propose specialist
ELIF context_insufficient OR risk == high:
→ Propose pause + clarification

### User-Initiated Recommendation Gate

Ответ на явный текущий запрос User проверяет:

- safety;
- eligibility;
- Context Sufficiency;
- competence boundary;
- explicit current refusal.

Quiet hours, cooldown и do-not-disturb для проактивности не блокируют ответ на
явный запрос User. Если safety или competence boundary блокируют запрошенное
действие, Journey переходит в S8.

### Proactive Readiness Gate

Для проактивной рекомендации дополнительно проверяются quiet hours, cooldown,
recent rejection, do-not-disturb, proactivity Consent и relevance decay.

Если proactivity заблокирована, Ayla не инициирует действие и не подменяет его
другим предложением. Допустимы только нейтральное acknowledgement текущего
контекста либо отсутствие сообщения.

### Success Criteria
- Ayla предложила следующий шаг с объяснением
- Пользователь согласился с рекомендацией или уточнил
- применимый gate пройден либо безопасно остановил действие

**Метрика:** Recommendation Acceptance Rate — доля пользователей, которые приняли рекомендацию.

## Stage 5 — Execution Layer

### Specialist Selection

**Правило:** Ayla предлагает 2-3 варианта специалистов с объяснением, почему каждый подходит.

**Карточка специалиста:**
Анна
Почему я выбрала её:
✓ Работает с мягким восстановлением
✓ Есть опыт работы с начинающими
✓ Удобное время вечером
✓ Подходит под твой запрос
Факты:
4.9 ★ (120 отзывов)
Ближайшее окно: завтра 19:00
60 минут, 3 500 ₽

**Запрещено:**
- ❌ "12 человек с похожей целью выбрали Анну" (скрытая манипуляция)
- ❌ Давление ("запишись сейчас, пока есть место!")
- ❌ Скрытие негативных отзывов
- ❌ Утверждение "Анна лучше Марии" без явной проверяемой системы критериев

### Provider Trust Model

**Цель:** Рекомендовать не "лучшего вообще", а подходящего под конкретный подтверждённый запрос пользователя.

**Ayla может учитывать только проверяемые критерии:**
- Подтверждённая квалификация и актуальность документов
- Заявленная специализация и подтверждённый перечень услуг
- Релевантный опыт
- Проверенные отзывы и устойчивые сигналы качества
- Пройденное обучение и сертификации, если они применимы к услуге
- Доступность, расположение, цена и формат
- Явные предпочтения и ограничения пользователя

**Правило объяснения:** Для каждого рекомендованного провайдера Ayla показывает критерии соответствия запросу и источник существенных фактов.

**Допустимо:** "Анна соответствует твоему запросу: работает с мягким восстановлением, принимает вечером и находится в пределах выбранного бюджета."

**Недопустимо:** "Анна — лучший мастер" или "Анна лучше Марии".

**Экономическая нейтральность:** Комиссия, тариф провайдера, рекламный бюджет и коммерческий приоритет не участвуют в `provider_match_score`.

**Недостаток данных:** Если квалификация, специализация или актуальность сведений не подтверждены, Ayla обозначает это и не превращает предположение в факт.

### Booking

**Правило:** Ayla помогает выбрать слот, подтвердить бронирование, оплатить (если нужно).

**Архитектура:**
User chooses specialist
↓
Ayla calls Ayla REST API (GET /api/v1/specialists/{id}/slots)
↓
Ayla shows available slots
↓
User confirms slot
↓
Ayla calls Ayla REST API (POST /api/v1/appointments)
↓
Backend creates Booking and returns its actual Booking State
↓
Backend publishes `booking.created`
↓
Provider/system confirmation transitions Booking to `confirmed`
↓
Backend publishes `booking.confirmed`
↓
Ayla shows user-facing confirmation

Если backend атомарно создаёт Booking в состоянии `confirmed`, он публикует
`booking.created`, затем `booking.confirmed` в том же transaction/outbox
boundary. User-facing confirmation показывается только после получения
authoritative confirmed state. Booking Request, Booking Created и Confirmed
Booking не используются как взаимозаменяемые термины.

### Confirmation

**Правило:** После записи Ayla:
- Подтверждает детали (кто, когда, где)
- Предлагает сохранить полезные предпочтения, если для Persistent Memory ещё
  нет подходящего purpose-specific Consent
- Предлагает напоминание

**Пример:**
Отлично, запись подтверждена.
Похоже, тебе удобнее вечерние записи. Сохранить это как предпочтение для
будущих подборов?

До подтверждения:

```yaml
storage_scope: session
memory_status: proposed
```

После подтверждения и Consent:

```yaml
storage_scope: persistent
consent_scope: booking_personalization
```

Строго необходимые operational facts активного Booking могут храниться по
операционному основанию, но не становятся автоматически глобальной User Model.

### Error Recovery

**Сценарий 1:** Нет свободных слотов
- **Действие:** Предложить альтернативу (другой мастер, другое время)
- **Пример:** "К сожалению, у Анны нет свободных слотов на этой неделе. Могу предложить Елену — она тоже специализируется на мягком восстановлении."

**Сценарий 2:** Оплата не прошла
- **Действие:** Объяснить причину, предложить повторить или выбрать другой способ
- **Пример:** "Оплата не прошла. Возможно, проблема с картой. Попробовать ещё раз или выбрать другой способ оплаты?"

**Сценарий 3:** Технический сбой
- **Действие:** Извиниться, предложить альтернативу (записаться позже, написать мастеру напрямую)
- **Пример:** "Извини, произошёл сбой. Могу попробовать записать тебя позже или дать контакты мастера, чтобы ты записалась напрямую."

### Success Criteria
- Booking достиг authoritative целевого состояния либо пользователь получил
  честное описание ошибки и Recovery path
- Ayla подтвердила только фактически достигнутое состояние
- Memory Proposal не стал Persistent Memory без применимого Consent

**Метрика:** Booking Success Rate — доля пользователей, которые успешно завершили запись.

## Stage 6 — Feedback Loop

### Feedback Collection

**Правило:** После действия Ayla спрашивает, как прошло.

**Прогрессивное раскрытие:**
Как прошло?
❤️ Отлично
🙂 Нормально
🙁 Не подошло

**Если негатив (🙁):**
Что именно не подошло?
Специалист
Результат
Формат
Ожидания
Другое

### Learning Signals

**Правило:** Ayla использует feedback для обновления модели пользователя по
proposed lifecycle model (planned source: ADR-0012):

**Явные сигналы:**
- "Отлично" → `current_relevance` гипотезы увеличивается
- "Не подошло" → `current_relevance` уменьшается, Ayla уточняет почему

**Неявные сигналы:**
- Пользователь не ответил на feedback → `current_relevance` не меняется (молчание ≠ отрицание)
- Пользователь отменил запись → Ayla уточняет причину

### Memory Proposal

**Правило:** Feedback создаёт Memory Proposal. Persistent Memory обновляется
только после sensitivity/purpose check и проверки применимого Consent.

**Пример:**
Пользователь: "Не подошло. Специалист был слишком навязчивый."
Ayla: "Похоже, тебе важен ненавязчивый подход. Сохранить это как предпочтение
для будущих подборов?"

Memory Proposal:

```yaml
memory_status: proposed
storage_scope: session
fact_key: specialist_preference
value: "ненавязчивый подход"
source: explicit
```

После явного подтверждения:

```yaml
memory_status: confirmed
storage_scope: persistent
consent_scope: provider_selection
provenance_preserved: true
```

### Success Criteria
- Пользователь дал feedback (хотя бы базовый)
- Ayla учла feedback в текущей сессии
- Persistent Memory обновлена только при наличии применимого Consent

**Метрика:** Feedback Response Rate — доля пользователей, которые дали feedback.

## Stage 7 — Long-term Relationship

### Retention Principles

**Правило:** Ayla возвращается только если есть полезный контекст. Не ради активности.

**Принципы:**
- **Уместность:** Ayla проверяет Proactive Readiness Gate перед проактивностью
- **Прозрачность:** Ayla объясняет, почему возвращается
- **Контроль:** Пользователь может отключить проактивность

### Proactive Interaction

**Правило:** Ayla может проактивно предложить действие, если:
- наступил подтверждённый пользовательский цикл или Goal milestone;
- пользователь ранее запросил напоминание;
- завершился согласованный план;
- изменилась доступность выбранного Provider;
- возник релевантный сезонный фактор здоровья или routine, но не коммерческая
  акция;
- пользователь не отключил проактивность и применимый Consent действует.

**Пример:**
Привет! Прошло 2 недели с твоего последнего массажа.
Как спина? Если хочешь, могу записать тебя к Анне на этой неделе.

### Proactive Readiness Gate (Long-term)

**Правило:** Перед проактивным предложением Ayla проверяет:
- Не отклонял ли пользователь похожие предложения недавно?
- Не сказал ли пользователь "не напоминай"?
- Не находится ли пользователь в "quiet hours"?

**Если Proactive Readiness Gate заблокировал:**
- Ayla не предлагает действие
- Ayla не предлагает substitute offer
- Ayla остаётся безмолвной либо даёт нейтральное acknowledgement без CTA, если
  сообщение уже было инициировано по иному допустимому основанию

### Success Criteria
- Пользователь вернулся к Ayla самостоятельно
- Пользователь не отключил проактивность
- Ayla помогла пользователю с новым намерением

**Метрика:** 30-Day Return Rate — доля пользователей, которые вернулись в течение 30 дней.

## Stage 8 — Boundary Handling

### Purpose

Boundary Handling — защитное состояние для ситуаций, в которых Ayla не может безопасно продолжать обычный Discovery, Recommendation или Execution.

**S8 не является провалом Journey.** Корректное ограничение, безопасная переориентация или направление к квалифицированному специалисту считаются полезным разрешением намерения.

### Entry Conditions

Ayla переходит в S8 при обнаружении:
- Медицинского запроса, требующего диагностики или лечения
- Признаков непосредственного риска для физического или психического здоровья
- Опасной цели снижения веса или признаков расстройства пищевого поведения
- Вопросов о назначении, отмене или изменении лекарств
- Травмы, острой или необъяснимой боли
- Запроса вне утверждённых предметных границ Ayla
- Недостаточного контекста при высокой цене ошибки

### Required Behavior

1. Остановить текущую рекомендацию и связанные действия.
2. Кратко назвать границу компетенции без постановки диагноза.
3. Объяснить известный риск простым языком, не усиливая тревогу.
4. Предложить безопасный следующий шаг: квалифицированного специалиста, экстренную помощь при явной срочности или новое безопасное намерение.
5. Не сохранять неподтверждённые медицинские выводы как факт о пользователе.
6. Зафиксировать `boundary_reason`, принятое решение и источник сигнала для аудита без избыточного сохранения чувствительных данных.

### Example

Пользователь: "Как мне убрать 15 кг за месяц?"

Ayla: "Такая скорость снижения веса может быть небезопасной. Я не буду составлять план с этой целью. Давай выберем более безопасный темп или подготовим вопросы для профильного специалиста."

### Exit Paths

- **S8 → S2:** Пользователь выбирает новое безопасное намерение; Discovery начинается заново с сохранением допустимого контекста.
- **S8 → S4:** Ayla предлагает только безопасную альтернативу или обращение к квалифицированному специалисту.
- **S8 → Exit:** Ayla прекращает предметную рекомендацию, если безопасного продолжения нет.

### Success Criteria

- Небезопасная рекомендация или execution не были выполнены
- Граница компетенции объяснена
- Пользователь получил безопасный следующий шаг
- Решение можно восстановить по audit trail без хранения лишних чувствительных данных

**Метрики safety:** critical false-negative count, upper confidence bound для
critical miss rate и false-positive UX guardrail. Нулевая наблюдаемая ошибка
на малой выборке не доказывает нулевой риск.

## Domain Journey — Nutrition Guidance

Питание является самостоятельным доменом Journey. Food Scanner — один из инструментов сбора контекста, а не определение домена.

### Goal

Поддержать безопасное, реалистичное и выполнимое намерение пользователя: изменение веса, улучшение режима питания, повышение энергии, поддержание формы или подготовка вопросов для специалиста.

### Discovery

Ayla собирает только минимально необходимый контекст:
- Цель пользователя и желаемый горизонт
- Текущие привычки и режим питания
- Что мешает соблюдать выбранный режим
- Предпочтения, доступность продуктов и бюджет
- Явно сообщённые ограничения, аллергии и противопоказания
- Предыдущие попытки и их результат

Food Scanner может уточнять фактический рацион, но не заменяет вопросы о цели, ограничениях и самочувствии. Отсутствие фотографии не блокирует Nutrition Journey.

### Recommendation

Ayla выбирает один из путей:

| Условие | Следующий шаг |
|---|---|
| Низкий риск, понятная цель | Небольшое изменение привычки или базовый план |
| Нужна персональная квалификация | Консультация профильного специалиста |
| Недостаточно контекста | Один минимально необходимый вопрос |
| Обнаружен safety-critical сигнал | Переход в S8 Boundary Handling |

Рекомендация не должна содержать диагноз, экстремальное ограничение калорий, обещание результата или назначение лечения.

### Execution and Feedback

Execution может быть планом на ограниченный период, одной привычкой, ведением дневника, использованием Food Scanner или записью к специалисту. Feedback оценивает выполнимость, самочувствие и полезность, а не только изменение веса.

### Success Criteria

- Пользователь получил безопасный следующий шаг, соответствующий его цели
- План выполним и не основан на стыде или радикальных ограничениях
- Ограничения и неопределённость обозначены
- При риске Journey перешёл в S8

**Метрика:** Nutrition Guidance Usefulness Rate — доля пользователей, подтвердивших полезность и выполнимость следующего шага.

# 5. Memory Interaction

## What Ayla Remembers

**Правило:** Ayla запоминает только то, что необходимо для помощи пользователю.

**Proposed классы знаний (planned source: ADR-0012):**

| Класс | Описание | Примеры | TTL |
|---|---|---|---|
| `verified_identity` | Проверенные, но исправляемые identity-атрибуты | Дата рождения, связанный ID | По identity/retention policy |
| `persistent_safety` | Долгосрочные safety-факты | Подтверждённая аллергия | Без автоматического удаления только по возрасту; с переподтверждением |
| `time_bounded_safety` | Временные safety-факты | Беременность, приём лекарств | По утверждённой safety/retention policy |
| `stable` | Устойчивые предпочтения | Любимый Specialist, предпочтительное время | Candidate: 365 дней |
| `ephemeral` | Временный контекст | "Завал на работе", "в отпуске" | Candidate: 14–30 дней |
| `hypothesis` | Предположения AI | "Вероятно, предпочитает вечер" | Candidate: 30 дней |

Числовые TTL в таблице являются design candidates, а не действующей retention
policy. До принятия профильного ADR они не разрешают автоматическое удаление
safety-critical сведений или бессрочное хранение персональных данных.

## When Memory is Created

**Правило:** сообщение, событие или вывод создают только `Memory Proposal`.
Persistent Memory создаётся и используется, только если есть purpose-specific
Consent, разрешающий соответствующие хранение и использование, а запись имеет
provenance, sensitivity и lifecycle metadata.

Допустимые источники proposal:
- пользователь явно сообщил значение (`source: explicit`);
- Ayla наблюдала разрешённое событие (`source: signal`);
- Ayla сделала вывод в пределах согласованной цели (`source: inferred`,
  `knowledge_class: hypothesis`).

Молчание, продолжение диалога и согласие на историю сообщений не являются
согласием на профилирование или сохранение inferred hypotheses.

**Примеры:**
- Пользователь сказал "я веган" → создаётся proposal с `source: explicit`
- Пользователь 3 раза записался вечером → создаётся `hypothesis` с `source: signal`
- Ayla вывела "вероятно, предпочитает мягкий массаж" → создаётся `hypothesis` с `source: inferred`

Обязательный flow:

Signal или Explicit Statement → Memory Proposal → Sensitivity and Purpose
Check → Consent Check → Persistent Memory либо Session Context only.

### MVP Memory Heuristic

До принятия ADR-0012 автоматический decay engine не реализуется.

1. `explicit` данные используются только в пределах исходной purpose, с учётом
   типа данных и времени получения.
2. Временные и изменяемые факты перед существенным использованием требуют
   повторного подтверждения.
3. Safety-critical информация не удаляется автоматически только по возрасту,
   но может перейти в состояние `confirmation_required`.
4. `inferred` и `signal` не используются как самостоятельное основание
   Substantial Recommendation.
5. Подтверждённая User гипотеза преобразуется в declared/confirmed Context с
   сохранением Provenance.
6. Полные TTL, decay и `current_relevance` откладываются до ADR-0012.

## When Memory is Used

**Правило:** Ayla использует Persistent Memory только в пределах цели и Consent,
для которых запись была сохранена:
- Персонализации рекомендаций (Stage 4)
- Понимания намерения (Stage 3)
- Пропускания повторяющихся вопросов (Stage 2)

**Пример:**
- Актуальное подтверждённое веганское предпочтение → Ayla учитывает его в
  пределах согласованной purpose
- Пользователь предпочитает вечер → Ayla предлагает вечерние слоты
- Ayla вывела "вероятно, предпочитает мягкий массаж" → Ayla предлагает мягкий массаж, но уточняет

## When Memory Must be Questioned

**Правило:** Ayla переспрашивает, если:
- `current_relevance` факта < 0.3;
- прошло больше TTL;
- есть противоречие;
- факт является временным, изменяемым или safety-critical и используется для
  существенного решения.

**Пример:**
- Пользователь сказал "я веган" 2 года назад → Ayla уточняет: "Ты всё ещё веган?"
- Ayla вывела "предпочитает вечер" 3 месяца назад → Ayla уточняет: "Тебе всё ещё удобнее вечер?"

# 6. Recommendation and Proactivity Gates

## Purpose

**User-Initiated Recommendation Gate** определяет, можно ли ответить
рекомендацией на явный текущий запрос User.

**Proactive Readiness Gate** — proposed механизм, который определяет, уместно
ли Ayla самостоятельно инициировать предложение (planned source: ADR-0012).

**Цель:** обеспечить безопасность ответа и предотвратить навязчивость,
respecting user autonomy (Конституция Ст. X).

## User-Initiated Recommendation Rules

Проверяются safety, eligibility, Context Sufficiency, competence boundary и
explicit current refusal. Quiet hours и настройки проактивности не блокируют
ответ на сообщение, которое User отправил самостоятельно.

## Proactive Suppression Rules

Дополнительные блокирующие факторы:

| Фактор | Описание | Действие |
|---|---|---|
| `explicit_do_not_disturb` | Пользователь сказал "не напоминай" | Жёсткая блокировка, без `reconsider_after` |
| `topic_cooldown_active` | Похожее предложение отклонено < 14 дней назад | Временная блокировка |
| `high_workload_context` | Эфемерный факт "завал на работе" активен | Эмпатия без CTA |
| `quiet_hours` | Настроенное окно "не беспокоить" | Отложить до `reconsider_after` |
| `proactivity_consent_missing` | Нет действующего разрешения на проактивность | Не инициировать сообщение |
| `low_relevance` | `current_relevance` базовой гипотезы < 0.2 | Не предлагать |

## User Communication

**Правило:** Если Proactive Readiness Gate заблокировал действие, Ayla:
- не инициирует действие;
- не предлагает альтернативу;
- остаётся безмолвной либо использует нейтральное acknowledgement без CTA,
  только если контакт уже возник по другому допустимому основанию.

**Примеры:**

**Жёсткий отказ:**
Пользователь: "Не напоминай мне о массаже"
Ayla: "Поняла. Больше не буду поднимать эту тему."

**Мягкий отказ:**
Пользователь: "Сейчас не до этого"
Ayla: "Поняла. Не буду сейчас поднимать эту тему.
Напомнить позже или оставить до твоего запроса?"

**Эмпатия без CTA:**
Пользователь: "У меня завал на работе"
Ayla: "Похоже, сейчас действительно напряжённо.
Надеюсь, скоро станет легче."

# 7. Cross-channel Experience

## MAX Bot

**Роль:** Primary channel для discovery, диалога, быстрых действий.

**Функции:**
- Первый контакт (Stage 1)
- Discovery (Stage 2)
- Intent Understanding (Stage 3)
- Recommendation (Stage 4)
- Быстрые действия (запись, отмена, перенос)
- Feedback (Stage 6)

## Mini App

**Роль:** Secondary channel для сложных действий.

**Функции:**
- Профиль пользователя
- Memory transparency (что Ayla "помнит")
- Food Scanner (когда нужен контекст)
- Wellness dashboard (post-pilot)
- Детали записи, оплата

## Context Continuity

**Правило:** Контекст сохраняется между каналами.

**Пример:**
- Пользователь начал диалог в MAX Bot
- Перешёл в Mini App для оплаты
- Вернулся в MAX Bot для feedback
- Ayla помнит контекст на всех этапах

**Архитектура:**
- MAX Bot и Mini App используют связанную channel identity согласно
  [[ADR-0009 Ayla Split-Domain Architecture]];
- персональный контекст Ayla доступен между каналами только в пределах Consent
  и purpose limitation; детали — planned ADR-0011;
- события (`booking.created`, `booking.confirmed`, `payment.completed`)
  синхронизируются через eventbus согласно
  [[ADR-0009 Ayla Split-Domain Architecture]].

# 8. Timing Rules

## First Value

**Правило:** Пользователь должен получить пользу в течение 5 минут.

First Value возникает внутри S2/S3 и может быть полезной переформулировкой,
обнаруженным ограничением или безопасным preliminary insight. Recommendation и
Execution не требуются для фиксации First Value.

**Метрика:** Time to First Value — время от первого сообщения до первого
подтверждённого полезного результата.

**Цель:** < 5 минут.

## Feedback Timing

**Правило:** Feedback delay является pilot default, configurable by Action
Class. Journey определяет семантику, а конкретные интервалы задаёт
Notification/Engagement Policy.

Начальные design defaults:

| Action Class | Feedback delay |
|---|---|
| booking experience | 30 минут после завершения flow |
| massage outcome | 24 часа после визита |
| training session | 4 часа после занятия |
| nutrition plan | 7 дней после начала |

## Re-engagement

**Правило:** Интервалы re-engagement и cooldown являются configurable pilot
defaults по Action Class, действуют только при применимом Consent и никогда не
используют молчание как положительный сигнал. Конкретные значения определяет
Notification/Engagement Policy.

# 9. Business Alignment

## Monetization Neutrality

**Правило:** Ayla не оптимизируется на запись или выручку (Конституция Ст. IV).

### Economic Neutrality Enforcement

Recommendation Engine не должен получать или использовать запрещённые
коммерческие признаки при candidate ranking:

- provider revenue;
- Booking Fee economics;
- subscription tier;
- advertising spend;
- paid placement;
- коммерческий приоритет Provider.

Гарантия должна подтверждаться allowlist полей Recommendation Candidate DTO,
ranking contract без запрещённых полей, schema/contract tests, feature logging
ranking decisions и audit test независимости результата от коммерческих
признаков. Конкретный технический контракт определяется Recommendation Engine
Specification или отдельным ADR.

Цена услуги может отображаться и использоваться как пользовательский Budget.
Booking Fee допустим в billing context после выбора и выполнения, но не в
provider ranking.

## Intent Resolution Types

**Правило:** Успешное разрешение намерения может быть разным:

| Тип | Описание | Пример |
|---|---|---|
| **Type A: Action Completed** | Пользователь записался, посетил, подтвердил пользу | Запись к мастеру |
| **Type B: Guidance Accepted** | Пользователь получил направление и признал полезным | "Тебе нужен врач, а не массаж" |
| **Type C: Self-improvement Started** | Пользователь начал действие (питание, тренировки, режим) | Начал пить воду |

**Метрика:**

Intent Resolution Rate = resolved intents / eligible intents.

Resolved outcome требует user-confirmed результата либо подтверждённого
выполнения. Для метрики фиксируются denominator, exclusion rules, resolution
window, multi-intent handling и различие user-confirmed/inferred resolution.

Полнота требуемого цикла измеряется отдельно через End-to-End Journey
Completion Rate.

Helpful Restraint считается Intent Resolution только при положительном
подтверждении: User согласился отложить действие, выбрал safe exit, подтвердил
полезность объяснения либо сам закрыл Intent как решённый. Молчание и отсутствие
жалобы не считаются подтверждением.

**Цель:** ≥ 60% для пилота.

## Pilot / Concierge Mode

Для первых 100-500 пользователей Ayla работает в Concierge Mode. Цель режима — проверить качество Journey и собрать доказательства для автоматизации до масштабирования.

### Required Operations

- **Post-hoc review:** низкорисковые навигационные, scheduling и обычные
  booking-сценарии не задерживаются; выборка проверяется после ответа
- **Pre-flight review:** существенные, но не экстренные чувствительные
  рекомендации, высокая неопределённость и значимые financial/privacy
  consequences удерживаются до проверки
- **Hard policy block:** emergency signal, явная угроза здоровью, запрос
  назначения/отмены лекарств, опасная цель снижения веса и иные критические
  границы немедленно получают deterministic boundary response; ожидание
  оператора не является условием безопасной остановки
- Ручная корректировка ranking только по критериям Provider Trust Model
- Короткое интервью после завершённого или прерванного сценария
- Структурированный сбор ошибок Intent, Discovery, Recommendation, Boundary Handling и Execution
- Еженедельный разбор false positive / false negative safety-срабатываний
- Сопоставление рекомендации, принятого действия и фактического результата

### Human Review Guardrails

- Пользователь заранее знает, когда взаимодействие может быть проверено человеком
- Доступ ревьюеров ограничен ролью и журналируется
- Ревьюер видит только минимально необходимый контекст
- Чувствительные данные не выгружаются в таблицы, чаты или неутверждённые инструменты
- Ручная корректировка не может вводить скрытый коммерческий приоритет
- Решение ревьюера и причина изменения сохраняются в audit trail

### Exit Criteria

Переход от Concierge Mode к автоматическому режиму допускается отдельно для
каждого Intent Type и Risk Level, когда:
- Достигнуты целевые Intent Recognition Accuracy и Intent Resolution Rate
- За согласованное окно нет critical false negative
- Upper confidence bound critical miss rate ниже утверждённого порога
- False-positive rate не превышает UX guardrail
- Проверено не менее утверждённого N сценариев для каждого Intent Type и Risk
  Level, включая red-team и adversarial cases
- Критические ошибки Recommendation и Execution отсутствуют в согласованном окне наблюдения
- Команда может объяснить ranking и восстановить путь принятия решения
- Подтверждена готовность rollback к ручной проверке

Автоматизация одного Intent Type и Risk Level не означает автоматизацию всех
доменов.

# 10. WOW Moment Specification

## Definition

**WOW = "Она сформулировала мою проблему лучше, чем я сам"**

**Почему это WOW:**
- Ayla не просто приняла запрос
- Ayla поняла контекст
- Ayla предложила безопасный путь

## When WOW Happens

**Правило:** WOW происходит на Stage 3 (Intent Understanding).

**Пример:**
Пользователь: "Хочу похудеть."
Ayla уточнила предыдущий опыт и ограничения.
Пользователь: "Начинаю, но через неделю бросаю."
Ayla: "Похоже, ключевая трудность — удержать выполнимый режим, а не найти
самую строгую диету. Давай выберем безопасный небольшой шаг."

## How to Create WOW

**Правило:** WOW создаётся через:
1. **Понимание контекста:** Ayla учитывает историю, ограничения, предпочтения
2. **Безопасный путь:** Ayla предлагает постепенные изменения, не радикальные
3. **Объяснение:** Ayla объясняет, почему именно это

# 11. Edge Cases

## Edge Case 1: Пользователь не знает, чего хочет

**Сценарий:** "Хочу что-нибудь сделать, но не знаю что"

**Действие:** Ayla помогает сформулировать через категории:
Давай начнём проще.
Что сейчас ближе?
Хочу лучше выглядеть
Хочу больше энергии
Хочу привести тело в форму
Хочу просто расслабиться

## Edge Case 2: Пользователь просит опасное

**Сценарий:** "У меня сильная боль в спине, найди массаж пожёстче"

**Действие:** Ayla переходит в S8, не подтверждает и не рекомендует сильное
воздействие, останавливает подбор услуги до safety clarification, задаёт только
минимальные вопросы о срочности и red flags и предлагает безопасный следующий
шаг.

**Пример:** "При сильной боли я не могу рекомендовать интенсивный массаж.
Уточню только несколько признаков, чтобы понять срочность и подсказать
безопасный следующий шаг. Если боль острая, появилась после травмы или есть
слабость/онемение, лучше обратиться за квалифицированной помощью."

## Edge Case 3: Ayla не знает

**Сценарий:** Пользователь задаёт вопрос, на который Ayla не может ответить.

**Действие:** Ayla честно признаёт неопределённость:
Я не уверена, что могу правильно подсказать в этой ситуации.
Чтобы не дать тебе неправильный совет, лучше уточню несколько деталей
или помогу найти специалиста.

## Edge Case 4: Пользователь хочет просто поговорить

**Сценарий:** Пользователь пишет личные сообщения, не связанные с self-care.

**Действие:** Ayla мягко возвращает к теме:
Могу помочь разобраться.
Если хочешь, давай попробуем понять, какой следующий шаг будет полезным.

## Edge Case 5: Пользователь передумал после записи

**Сценарий:** "Не хочу идти к мастеру, отмени запись"

**Действие:** Ayla отменяет и уточняет причину:
Поняла. Могу отменить запись.
Расскажи, что изменилось?
Передумал(а)
Не подходит время
Нашёл(ла) другого специалиста
Другое
Это поможет мне лучше подбирать варианты в будущем.

## Edge Case 6: Пользователь недоволен результатом

**Сценарий:** "Мастер был ужасный, мне не понравилось"

**Действие:** Ayla признаёт проблему и предлагает решение:
Мне жаль, что так получилось. Это не тот опыт, который я хотела для тебя.
Давай разберёмся:
Что именно не понравилось?
Подход мастера
Результат
Атмосфера
Время
Что я могу сделать?
Подобрать другого мастера с учётом твоих пожеланий
Помочь оставить отзыв
Предложить альтернативу
Что для тебя сейчас важнее?

# 12. Anti-patterns

## Anti-pattern 1: Ayla удивляет интеллектом

**Плохо:** "Я AI с памятью, который знает тебя лучше, чем ты сам"

**Хорошо:** "Помогу разобраться, что тебе сейчас нужно"

## Anti-pattern 2: Ayla требует правильного формулирования

**Плохо:** "Выберите вид массажа из списка"

**Хорошо:** "Расскажи, что беспокоит"

## Anti-pattern 3: Ayla давит

**Плохо:** "Запишись сейчас, пока есть место!"

**Хорошо:** "Есть окно завтра в 19:00. Записать?"

## Anti-pattern 4: Ayla скрывает работу памяти

**Плохо:** "Я знаю, что ты предпочитаешь вечер" (без объяснения, откуда)

**Хорошо:** "Ты упоминал, что тебе удобнее вечер. Сохранить это как
предпочтение для будущих подборов?"

## Anti-pattern 5: Ayla заменяет специалиста

**Плохо:** "У тебя травма спины. Делай это упражнение"

**Хорошо:** "Похоже, нужна консультация специалиста. Могу найти врача рядом."

# 13. Metrics

## User Value Metrics

| Метрика | Описание | Цель |
|---|---|---|
| **Intent Resolution Rate** | Resolved intents / eligible intents с explicit resolution rules | ≥ 60% |
| **End-to-End Journey Completion Rate** | Доля Journey, завершивших требуемый для Action Class цикл | Определить baseline в пилоте |
| **Time to First Value** | Среднее время от первого сообщения до первого полезного действия | < 5 мин |
| **Trust Score** | Средняя оценка доверия (1-5) после взаимодействия | ≥ 4.0 |
| **Critical Boundary Miss Rate** | Critical false negatives / проверенные critical boundary-сценарии | 0 observed; confidence threshold задаётся safety policy |
| **Boundary False-positive Rate** | Ложные блокировки / проверенные безопасные сценарии | UX guardrail задаётся safety policy |
| **Helpful Restraint Acceptance Rate** | Явно принятые restraint outcomes / показанные restraint decisions | Определить baseline в пилоте |
| **Nutrition Guidance Usefulness Rate** | Доля пользователей, подтвердивших полезность и выполнимость nutrition-рекомендации | Определить baseline в пилоте |

## Journey Quality Metrics

| Метрика | Описание | Цель |
|---|---|---|
| **First Contact Completion Rate** | Доля пользователей, которые завершили Stage 1 | ≥ 80% |
| **Discovery Completion Rate** | Доля пользователей, которые завершили Stage 2 | ≥ 70% |
| **Intent Recognition Accuracy** | Доля правильно распознанных намерений | ≥ 85% |
| **Recommendation Acceptance Rate** | Доля пользователей, которые приняли рекомендацию | ≥ 50% |
| **Booking Success Rate** | Доля пользователей, которые успешно завершили запись | ≥ 90% |
| **Feedback Response Rate** | Доля пользователей, которые дали feedback | ≥ 40% |
| **7-Day Return Rate** | Доля пользователей, которые вернулись в течение 7 дней | ≥ 30% |
| **30-Day Return Rate** | Доля пользователей, которые вернулись в течение 30 дней | ≥ 20% |

## Business Metrics

Business Metrics измеряются отдельно и не входят в функцию оптимизации рекомендации:

| Метрика | Назначение |
|---|---|
| **Completed Bookings** | Количество завершённых записей |
| **GMV** | Общая стоимость завершённых транзакций |
| **Net Booking Fee Revenue** | Фактически полученный Booking Fee после возвратов и платёжных расходов |
| **Provider Activation Rate** | Доля подключённых провайдеров, получивших первую завершённую запись |
| **Provider Retention** | Доля активных провайдеров, продолжающих работу в выбранном периоде |
| **Booking Conversion** | Доля релевантных предложений записи, завершившихся подтверждённой записью |

**Правило приоритета:** Рост Business Metrics не считается успехом, если
ухудшились Trust Score, Critical Boundary Miss Rate, Intent Resolution Rate
или право пользователя отказаться.

**Запрещено:** Оптимизировать ranking на GMV, Booking Fee, тариф провайдера или количество записей любой ценой.

## Failure Criteria

**Правило:** Если User Value Metric ниже порога, продукт пересматривается независимо от Business Metrics.

| Метрика | Порог провала |
|---|---|
| Intent Resolution Rate | < 50% |
| Trust Score | < 3.0 |
| Critical Boundary Miss Rate | Любой critical false negative требует incident review |
| Booking Success Rate | < 80% |
| 7-Day Return Rate | < 20% |

## Example Journeys

### Journey 1: "Хочу восстановиться"

**Stage 0:** Пользователь увидел пост "Устала после работы? Ayla подберёт, что тебе нужно за 2 минуты"

**Stage 1:** Пользователь открывает MAX Bot, выбирает "Я устала и хочу восстановиться"

**Stage 2:** Ayla задаёт 3 вопроса:
- "Где чувствуешь напряжение?" — "Спина, шея"
- "Как давно?" — "Последнюю неделю"
- "Есть ли ограничения?" — "Нет"

**Stage 3:** Ayla понимает намерение: "восстановиться после нагрузки"

**Stage 4:** Ayla рекомендует:
Похоже, тебе сейчас нужно восстановление после нагрузки.
Я бы предложила расслабляющий массаж спины и шеи.
Это снимет напряжение и поможет почувствовать разницу уже сегодня.
Вот 2 проверенных мастера:
Анна (4.9 ★, есть окно сегодня в 19:00)
Мария (4.8 ★, есть окно завтра в 18:30)
Почему я рекомендую Анну: у неё есть окно сегодня вечером.
Записать к Анне?

**Stage 5:** Пользователь записывается к Анне

**Stage 6:** Через 2 часа Ayla спрашивает feedback. Пользователь отвечает "Отлично!"

**Stage 7:** Через 2 недели Ayla напоминает: "Как спина? Если хочешь, могу записать тебя к Анне снова."

### Journey 2: "Хочу похудеть"

**Stage 0:** Пользователь увидел рекламу "Не знаешь, с чего начать? Ayla поможет"

**Stage 1:** Пользователь открывает MAX Bot, выбирает "Хочу изменить тело или питание"

**Stage 2:** Ayla задаёт 3 вопроса:
- "Какая цель?" — "Похудеть на 10 кг"
- "Что мешает?" — "Сложно держать режим"
- "Есть ограничения?" — "Нет"

**Stage 3:** Ayla понимает намерение: "улучшить форму тела, но сложно удерживать режим"

**Stage 4:** Ayla рекомендует (WOW):
Похоже, ключевая трудность — удержать выполнимый режим, а не найти самую
строгую диету. Давай выберем безопасный небольшой шаг. Могу помочь сформировать
вопросы для плана или подобрать подходящего специалиста.

**Stage 5:** Пользователь выбирает "Подобрать тренера"

**Stage 6:** Пользователь записывается к тренеру

**Stage 7:** Через неделю Ayla спрашивает feedback. Пользователь отвечает "Нормально, но сложно держать режим"

**Stage 7 (продолжение):** Ayla использует feedback в текущем Context и
предлагает сохранить изменяемое предпочтение только через Memory Proposal и
Consent flow. Проактивное продолжение возможно после Proactive Readiness Gate.

### Journey 3: Boundary Handling

**Stage 1:** Пользователь пишет: "Хочу сбросить 15 кг за месяц и почти не есть"

**Stage 2:** Ayla фиксирует цель и обнаруживает safety-critical сигнал.

**Stage 8:** Ayla останавливает обычный Nutrition Journey, обозначает риск и не составляет экстремальный план.

**Safe exit:** Пользователь выбирает безопасный темп и возвращается в Stage 2 либо получает предложение обратиться к профильному специалисту.

## Journey State Machine

State machine является нормативным представлением переходов. Интерфейс может скрывать технические состояния, но не может обходить их условия входа и выхода.

`SR` — operational Recovery substate, а не дополнительный Journey State.
Он отделяет техническое восстановление от Outcome Feedback и не меняет
канонический набор S0-S8.

```yaml
states:
  acquisition:
    id: S0
    enter_on:
      - acquisition_trigger_received
    exit_on:
      - user_started_interaction

  first_contact:
    id: S1
    enter_on:
      - user_started_interaction
    exit_on:
      - initial_request_received

  discovery:
    id: S2
    enter_on:
      - initial_request_received
      - intent_shift_detected
      - safe_reentry_selected
    exit_on:
      - context_sufficient
      - user_declined_questions

  intent_understanding:
    id: S3
    enter_on:
      - context_sufficient
      - user_declined_questions
    required_checks:
      - intent_classified
      - confidence_evaluated
      - safety_evaluated
    exit_on:
      - intent_confirmed

  recommendation:
    id: S4
    enter_when:
      all_of:
        - intent_confirmed
        - applicable_recommendation_gate_passed
    required_checks:
      - safety_evaluated
      - recommendation_explained
    exit_on:
      - user_selected_action
      - clarification_requested
      - recommendation_declined

  execution:
    id: S5
    enter_when:
      all_of:
        - user_selected_action
        - action_confirmed
    exit_on:
      - action_completed
      - action_cancelled
      - execution_failed

  feedback:
    id: S6
    enter_on:
      - action_completed
    exit_on:
      - feedback_recorded
      - feedback_window_closed

  recovery:
    id: SR
    enter_on:
      - execution_failed
    required_actions:
      - explain_failure_without_internal_leak
      - preserve_idempotency
      - offer_retry_or_safe_recovery
    exit_on:
      - recovery_completed
      - interaction_closed

  long_term:
    id: S7
    enter_on:
      - feedback_recorded
      - feedback_window_closed
    exit_on:
      - new_intent_received
      - user_disabled_proactivity

  boundary_handling:
    id: S8
    enter_on:
      - boundary_detected
      - safety_critical_signal_detected
    required_actions:
      - stop_current_recommendation
      - explain_boundary
      - offer_safe_next_step
      - write_minimal_audit_event
    exit_on:
      - safe_reentry_selected
      - safe_alternative_allowed
      - interaction_closed

global_transitions:
  intent_shift_detected:
    from: [S1, S2, S3, S4, S5, S6, S7]
    to: S2
    actions:
      - preserve_permitted_context
      - invalidate_unconfirmed_action
      - preserve_confirmed_external_action_until_explicit_cancel
      - rerun_safety_evaluation

  boundary_detected:
    from: [S1, S2, S3, S4, S5, S6, S7]
    to: S8

  user_stopped_interaction:
    from: [S1, S2, S3, S4, S5, S6, S7, S8]
    to: exit
```

### State Machine Invariants

1. S4 недоступен без подтверждённого Intent и выполненной safety-проверки.
2. S5 недоступен без явного подтверждения действия пользователем.
3. S8 имеет приоритет над Recommendation и Execution.
4. Intent Shift отменяет неподтверждённое действие старого Intent.
5. Уже подтверждённая запись, платёж или иное внешнее действие не отменяются молча; для отмены требуется явное подтверждение пользователя.
6. Контекст переносится между состояниями только в пределах согласия, цели использования и правил памяти.
7. Повторное техническое событие не должно создавать дублирующее действие; execution-команды должны быть идемпотентными.
8. Каждый переход в S8 и каждая ручная корректировка Concierge Mode должны быть восстановимы по audit trail.
9. S2 не переходит непосредственно в S4; fast path всегда выполняет S3.
10. `execution_failed` ведёт в Recovery, а не в Outcome Feedback.
11. Proactive suppression не блокирует ответ на явный текущий запрос User.
