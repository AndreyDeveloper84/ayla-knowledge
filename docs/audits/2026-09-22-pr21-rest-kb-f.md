# Остаток ayla-knowledge PR #21 на отдельное утверждение (KB-F, DRF-2270)

**Дата:** 2026-09-22 · **PR #21:** `canon/recommendation-v1.0-proposed`,
голова `dfd9595d`, база `207eeb63` · **Ветка KB-F:**
`canon/drf2270-pr21-rest` поверх KB-E (DRF-2263).

## Сводка для владельца

**Что это.** Вы решили 21.09 (журнал главного окна CD §71 п.1, вне git):
«Полезные изменения из PR #21 собрать отдельно, описать простыми словами и
представить на самостоятельное утверждение». Здесь собраны все
41 изменение, которые KB-E отложил как «вне предмета», и пять остатков
A2 (DecisionReadiness, safety), которые KB-E сознательно не взял.

**Счёт.** Перенесено — **46** изменений (41 «вне предмета» + 5 остатков
A2). Не перенесено из-за конфликта с вашими решениями — **12** мест: они
названы в таблице и в самих документах помечены «не перенесено» или
«〔KB-F: …〕».

**Главное, о чём вы решаете (по сути 6 вещей):**

1. **Рекомендация отвечает «что сделать», а не «куда записаться».** На
   карточке C04 — направление, объяснение и три кнопки; услуга, мастер,
   цена и время — только на следующем экране C05.
2. **Ayla рекомендует только проверенные вами услуги** (`VERIFIED`). Если
   таких нет — честное «нечего рекомендовать», каталог и запись остаются.
3. **Ответ «при боли или отёках сначала один вопрос о здоровье».** Пока нет
   утверждённой таблицы опасных сигналов, при таком смысле Ayla не
   рекомендует, а спрашивает.
4. **События о рекомендациях другие.** «Принял рекомендацию» и «отказался»
   снимаются; вместо них — «спросил почему», «попросил другой вариант»,
   «перешёл к вариантам», «начал запись».
5. **Два часа — срок, когда рекомендацией можно воспользоваться, а не
   срок её хранения.** Запись хранится дольше, чтобы доказать, какая
   рекомендация привела к записи.
6. **Порядок в документах.** Старые разборы — в архив, старая редакция
   Journey — в папку `history/`, ADR-0013 — «заменён», метка статуса у
   intent-реестра — как у самой спецификации.

**Если не утвердите ничего** — все документы возвращаются к состоянию
KB-E: контракт v0.5, реестр событий v0.6, остальное как до PR #21. KB-E
от KB-F не зависит.

**Статусы.** KB-F ничего не делает утверждённым: контракт — `draft /
proposed` v0.6; BOT-003, UX Addendum, Final Reconciliation — `review /
candidate`, как их ставил PR #21. Номер «v1.0» контракту не дан: без
частей, отклонённых вашими решениями, он не равен тому, что PR #21 называл
«v1.0 = v0.4 + A1 + A2».

### Контракт рекомендаций (`05 Architecture/Ayla MVP Recommendation Contract.md` → v0.6)

- **1.2 Предмет рекомендации — «что сделать».** В записи рекомендации
  хранится направление; тип действия уходит к вариантам исполнения. ·
  *#21: ваше решение B2 «Recommendation = WHAT».* · **Не утвердить:**
  запись остаётся как в v0.4 — `action_type` внутри рекомендации.
- **1.4 ост. Поле `readiness_state` — только для замера.** В запись
  пишется оценка «хватало ли данных», но она ничего не решает. · *#21:
  замер порогов в тени (C1).* · **Не утвердить:** оценки в записи нет,
  порог нечем замерить по рекомендациям.
- **1.5 Версии правил безопасности и каталога в записи.** В каждой
  рекомендации видно, по какой версии правил её строили. · *#21: канон
  v1.1 §7.2, §14.6.* · **Не утвердить:** при разборе инцидента не видно,
  какие правила действовали.
- **1.6 `expires_at` → `actionable_until`.** Два часа — срок действия
  предложения, не срок хранения записи. · *#21: B13.* · **Не утвердить:**
  имя поля по-прежнему читается как «запись удаляется через 2 часа».
- **1.7 Семантическое разрешение.** Один шаг «понять, чего человек хочет»
  с необязательной целью и одним уточняющим вопросом за ход (для человека —
  исход `CLARIFY`). · *#21: A1, WD D-1, D-6.* · **Не утвердить:** остаются
  два шага «цель → результаты» из v0.5.
- **1.8 / 1.23 ост. DecisionReadiness — только тень.** Движок считает,
  «можно ли уже рекомендовать», но вопросов не задаёт; что делать —
  решает минимальный выбор AYLA-DEC-0097. · *#21: канон v1.1 Decision 5,
  C1.* · **Не утвердить:** в контракте нет описания тени.
- **1.9 ост. Четыре состояния безопасности на этапе 9.** «Нормально /
  уточнить / осторожно / стоп» (+ «неизвестно», «не применимо»). · *#21:
  канон v1.1 Decision 4.* · **Не утвердить:** есть только «допуск» или
  «граница».
- **1.10 Этап 16 — только проверенные услуги.** · *#21: C2.* · **Не
  утвердить:** этап «услуги / доступность» без правила `VERIFIED`.
- **1.11 Три снимка вместо одного.** Отдельно фиксируются решение,
  варианты исполнения и сама запись. · *#21: B10.* · **Не утвердить:**
  ADR-0013 остаётся открытым предложением с одним снимком.
- **1.12 Только `VERIFIED`, без запасной ветки; порядок ранжирования
  мастеров.** Ноль проверенных услуг — «нечего рекомендовать», а не

- **1.13 Альтернативы — по кнопке.** Другие варианты открываются только
  «Другой вариант». · *#21: B4.* · **Не утвердить:** контракт допускает
  показ альтернатив сразу.
- **1.14 События рекомендаций.** Снимаются «принял» / «отказался»;
  добавляются «почему», «другой вариант», «перешёл к вариантам», «начал
  запись». · *#21: B8.* · **Не утвердить:** «принял» остаётся — его легко
